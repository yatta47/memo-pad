## 0. 前提

### 0.1 本番化で追加する範囲（PoC に無いもの）

| 区分 | 内容 |
|---|---|
| Collector（情報収集） | ① DB クエリログ（PostgreSQL / BigQuery 等）→ READS / WRITES と Evidence、② API Gateway / ALB アクセスログ → CALLS、③ OpenAPI 仕様・Git リポジトリ → PROVIDES / 申告済み CALLS。未知の接続元は Unknown として自動起票 |
| 通知 | 鮮度・ズレ検知の週次ダイジェスト（Slack / メール）。責任チーム宛に配信 |
| 認証・権限 | SSO（既存 IdP 連携）。閲覧 / 編集（Unknown の特定、関係の承認）の 2 ロール |
| 変更レビュー連携 | Pull Request や変更申請から影響分析 API を呼び、結果をコメントとして付ける |
| 運用基盤 | IaC、CI/CD、監視・ログ、バックアップ、ステージング環境、監査ログ |
| データ移行 | fixture → 実データ（最初の対象システム群）。名寄せルールの整備 |

|---|---|---|---|

## 1. AWS と Google Cloud の比較

### 1.1 メリット・デメリット

| 観点 | AWS | Google Cloud |
|---|---|---|
| Graph DB の選択肢 | **AuraDB**（コード変更ほぼ無し）と **Neptune**（Bolt + openCypher。制約・インデックスの書き換えなど小〜中規模の修正）の 2 択。純正でも Cypher 系が使える | **AuraDB**（コード変更ほぼ無し）。純正の **Spanner Graph** は GQL + 専用クライアントで、Graph 層の書き直しが必要（約 1.5〜2 人月） |
| コンテナ実行 | ECS Fargate。タスク定義・ALB・サービス検出など部品が多く、初期構築に手間がかかる | Cloud Run。URL が即座に得られ、最小インスタンス数の指定だけで HA。構築が速い |
| 認証 | Cognito は設定項目が多い。ALB の OIDC 連携なら比較的簡単 | IAP で LB 前段に SSO を数手順で付けられる（Google Workspace 利用企業なら特に簡単） |
| ログ収集（Collector の入力） | CloudWatch Logs / RDS ログ / S3 の 3 系統。社内システムが AWS 上なら取得元に近い | Cloud Logging に集約されやすく、Log Sink → BigQuery でクエリログ分析がしやすい |
| LLM の調達 | Bedrock で Claude を同一請求・同一 VPC 内で利用可（Claude Opus 5.5 / Sonnet 5.5 対応） | Vertex AI で Claude を利用可（同様） |
| 閉域接続 | Aura は Enterprise ティアで PrivateLink。Neptune は VPC 内 | Aura は Enterprise ティアで Private Service Connect。Spanner は VPC-SC |
| 運用コスト | NAT Gateway、ALB の固定費が乗りやすい | 最小構成の固定費が小さい。Cloud Run は無料枠も大きい |
| 人材・ナレッジ | 国内の経験者が多く、SIer への発注もしやすい | 経験者はやや少ない。BigQuery 中心のデータ基盤がある企業なら親和性が高い |
| **最大の判断要因** | **対象システム（監視したい側）がどこで動いているか。** ログの取得元と同じクラウドに置くのが、Collector の実装・費用・権限管理のすべてで有利 | 同左 |

### 1.2 結論の出し方

1. **監視対象システムの大半が AWS にある → AWS**。Graph DB は初年度 AuraDB Professional、拡大時に Neptune か Aura Enterprise を再評価。
2. **監視対象が Google Cloud 中心、または BigQuery にログが集まっている → Google Cloud**。Graph DB は AuraDB（Spanner Graph は書き直し費用が見合う規模になってから）。
3. **両方に散っている → 社内の運用スキルがある側**。Collector は各クラウドのログを読みに行く形になるので、どちらに置いても越境は発生する。
4. どちらでも Frontend / Backend / Collector のコードは共通で、クラウド依存は IaC・認証・ログ取得の 3 箇所に閉じる。**後からの乗り換えは可能**（Aura を使う限り DB 移行は不要）。

## 5. AI 活用の検討

### 5.1 原則

1. **Graph が決め、AI は提案する。** 影響分析・迂回判定・鮮度判定は決定論のまま。AI は「候補を出す」「説明する」「下書きを書く」役。判断の根拠がログと Ontology にあることを崩さない。
2. **AI の出力は必ず Evidence 付きの「提案」として Graph に入れる。** `observation_type=proposed` の Relation として保存し、人が承認して初めて `declared` になる。誤抽出が静かに台帳を汚さない。
3. **人の作業時間が最も消えている場所から順に入れる。** §3.3 で見たとおり費用の本体は人件費。AI の価値は「名寄せ」「申告の下書き」「説明文」の時間削減で測る。
4. **モデルは用途で使い分ける。** 大量・定型は Claude Sonnet 5.5、コード読解や設計提案は Claude Opus 5.5。どちらも Bedrock / Vertex AI 経由で調達でき、データが外部に出ない構成にできる。

### 5.2 候補の一覧と評価

| # | 活用箇所 | 何をするか | 効果 | リスク | 難度 | 優先 |
|---|---|---|---|---|---|---|
| 1 | **コード・定義からの依存抽出（Collector の補助）** | リポジトリの ORM 定義・SQL・OpenAPI・設定ファイルから「このアプリはどのテーブルを読み書きし、どの API を呼ぶか」を抽出し、`proposed` Relation と Evidence（ファイルパス・行）を生成 | **大**。申告（declared）の整備を人手からほぼ自動へ。「使われていない申告」「申告のない利用」の検知精度が上がる | 誤抽出（動的 SQL、間接呼び出し）。承認フローで吸収 | 中 | **1** |
| 2 | **Unknown の名寄せ候補と理由** | 接続元 IP・DB ユーザー・時刻・サブネット・リポジトリ内の設定値を突き合わせ、候補を順位付けし「なぜそう考えるか」を根拠付きで説明。今はヒューリスティック | **大**。Unknown の解決に最も時間がかかっており、ここが詰まると台帳が陳腐化する | 誤った特定。候補提示のみで確定は人 | 低〜中 | **1** |
| 3 | **影響分析へのコメント生成** | 影響を受ける各対象について「どの経路で・何が壊れうるか・確認すべきこと」を、経路と Evidence を根拠に文章化 | 中〜大。経営層・他チームへの説明コストが下がる。PR コメントの本文にもなる | 根拠の無い推測を書く恐れ → 経路と Evidence 以外を参照させない | 低 | **1** |
| 4 | **変更レビュー（PR / 変更申請）への自動コメント** | マイグレーションや OpenAPI 差分から変更対象を特定 → 影響分析 API → 結果と #3 の説明を PR にコメント。Unknown が残っていれば警告 | **大**。「変更前に地図を見る」を強制でき、陳腐化対策にもなる | 誤検知によるノイズ。閾値とサイレント期間で調整 | 中 | **2** |
| 5 | **改善策の提案** | ルール逸脱（直接参照、申告なし利用、責任チーム未設定）に対し、是正案を生成。例: 「Billing App の直接 READ を置き換えるため、Customer API に `GET /v1/customers/{id}?fields=name,email` を追加」。API 仕様の下書きまで出す | 中〜大。是正の着手が速くなる | 現実の制約（性能、契約）を知らない提案。提案は「たたき台」と明記 | 中 | **2** |
| 6 | **新規データ設計レビューの深掘り** | 現在の決定論判定に加え、スキーマ案（カラム・キー・参照）と、既存 Address との関係の選択肢を比較表で提示 | 中。設計レビュー会議の準備時間を削減 | 既存の制約を見落とす | 低 | 2 |
| 7 | **週次ダイジェストの文章化** | 鮮度・ズレ検知の結果をチーム別に要約し、「今週やるべき 3 件」の形で配信 | 中。通知が読まれる確率が上がる | 低 | 低 | 2 |
| 8 | **自然言語での問い合わせ** | 「customer の email を変えたら誰に相談？」→ 影響分析 API を呼んで回答。MCP ツールとして Graph を公開 | 中。経営層が自分で聞ける | Cypher を直接生成させると誤答・過負荷。**既存 API のみを呼ぶ**形に限定 | 中 | 3 |
| 9 | **Ontology の整備支援** | 新しい種類のログや資産（Kafka トピック、S3 バケット等）が現れたとき、Object Type / Relation Type の追加案を提示 | 中（拡張時） | 低 | 中 | 3 |
| 10 | **業務データ（概念）への自動分類** | 新しいテーブル・API を既存の業務データに紐付ける候補を提示（REPRESENTS / OPERATES_ON） | 中。概念層の維持コストを下げる | 誤分類 → 承認フロー | 低 | 3 |

### 5.3 推奨する導入順

**第 1 弾（本番化と同時）: #1 依存抽出、#2 名寄せ候補、#3 影響コメント**
台帳を「埋める」「正す」「説明する」の 3 点で、人の作業が最も多い場所。いずれも Graph のデータを入力にし、出力は提案か文章なので、判断の決定論性を崩さない。

**第 2 弾（運用開始後 3 か月）: #4 PR 連携、#5 改善提案、#6 設計レビュー深掘り、#7 ダイジェスト**
利用者の変更フローに組み込み、「使わないと仕事が進まない」状態を作る段階。

**第 3 弾（全社展開時）: #8 自然言語問い合わせ、#9 Ontology 支援、#10 概念分類**
対象が増え、人手での分類が追いつかなくなってから。

### 5.4 組み込み方（アーキテクチャ）

```
  リポジトリ / OpenAPI / ログ ──► Collector ──► 構造化できる部分は決定論で Relation 化
                                      │
                                      └─► 非構造部分（SQL 文字列・ORM・README）を LLM に渡す
                                               │  入力: 該当ファイル断片 + Ontology の型定義 + 既存の Object 一覧
                                               ▼
                                   proposed Relation + Evidence（source_ref = ファイル:行）
                                               │
                                   承認キュー（UI の「未承認の提案」）── 人が承認 → declared
                                               │                         却下 → 理由を保存（次回の抑制に使う）
  影響分析 API ──► 結果（経路・Evidence）──► LLM が説明文を生成 ──► 画面 / PR コメント / ダイジェスト
```

- LLM への入力は **Graph から取り出した事実（Object・Relation・Evidence・経路）と、Ontology の定義**に限定する。「知らないことは知らない」と答えさせ、根拠の無い固有名詞を出させない。
- 出力は構造化（JSON Schema）で受け取り、Graph に書く前にスキーマと Ontology の from/to 制約で検証する（PoC の seed が fixture を検証しているのと同じ経路）。
- すべての AI 提案に `confidence` と `model` を Evidence として残し、承認・却下の履歴から精度を測る。

### 5.5 モデル選択と調達

| 用途 | モデル | 理由 |
|---|---|---|
| #3 #7 説明文・要約（大量・定型） | Claude Sonnet 5.5 | 速度と費用。入力は Graph の事実のみなので高度な推論は不要 |
| #1 #5 #6 コード読解・設計提案 | Claude Opus 5.5 | 誤抽出・見落としのコストが高い。件数は少ない |
| #2 名寄せ候補 | Sonnet 5.5（候補順位） → 迷う場合のみ Opus 5.5 | |
| 調達 | AWS: Amazon Bedrock、GCP: Vertex AI | データをクラウド境界の内側に留められる。Anthropic API 直接でも可 |

### 5.7 効果の見積もり（§3.3 の人件費に対して）

| 作業 | 現状（人手） | AI 導入後 | 削減 |
