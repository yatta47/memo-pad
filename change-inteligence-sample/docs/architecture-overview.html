Change Intelligence PoC · 説明資料

デモ対象の 4 システムと、それを地図にする PoC の全体像

Customer を中心に、正規の API 利用と非正規の DB 直接参照が混在した「現実の構造」を 1 枚で示します。この構造をそのまま Knowledge Graph に取り込み、変更影響・未特定の利用元・ルール逸脱・鮮度のズレを機械的に答えるのが本 PoC です。

1. デモ対象の 4 システム構成図

外側の箱がシステム、その中がアプリケーション（App）。その内側に、外に提供する窓口（API）と、そのサービスだけが更新するデータベース / テーブル（主要カラム）が入ります。箱をまたぐ線が依存で、線の種類が「正規か・観測されているか」を表します。

2. 各システムの責務と見せたい関係

システム責務 / 構成PoC で見せる関係

4. PoC 自体の構成

図 1 の世界を Knowledge Graph として取り込み、質問に答える側のシステム。すべて Docker Compose で起動し、Neo4j に触るのは Backend だけ。

6. この構造で答えられる質問

  1. customer テーブルを変えたら？ → Billing / Analytics / UNKNOWN-001 が直接、Order は API 経由で間接。相談先は 4 チーム。
  2. Customer API を変えたら？ → 呼び出している Order と Billing、提供元の Customer Team。
  3. ルールから外れている利用は？ → 赤い線 3 本。Billing は正規 API を使いながら迂回している。
  4. UNKNOWN-001 は誰？ → 根拠（rpt_reader、subnet=analytics-legacy、03:30）から Legacy Batch と特定し、履歴を残す。
  5. 台帳と実態はずれていないか？ → Analytics の直接参照は 8/20 以降観測なし、Order → PUT は申告のみ、Billing の API 利用は申告なし。
  6. 配送先住所を新しく作るべきか？ → customer_address / Address と重なる。「注文時点の記録」なので新設して Address を参照する案も提示。
  7. Get Invoice API は廃止できるか？ → 利用先が無く廃止可。customer テーブルは 5 件の利用先があり廃止不可。

根拠（Evidence）はすべての線に付く: 出所（DB クエリログ / API ゲートウェイログ / API 仕様書 / 通信ログ）、初回・最終観測日時、確からしさ、申告か観測か。
