### STEP 2: catalog/ → PostgreSQL（Postgres MCP 経由）

発話: `docs/prompts/02-insert.md` の通り。

実行経路: このセッションは life-project 側で起動していたため、MCP クライアント（Python）から Postgres MCP の `execute_sql` を呼ぶ形で同じ経路を通した。当日は Claude Code / Cursor がツールを直接呼ぶ。

結果:
- DDL: `cases` テーブル（9列、`id` 主キー、`confirmed_at` は date、効果2列は `DEFAULT ''`）
- INSERT: 12件ずつ4回、各回 11〜13KB の SQL リテラル。`ON CONFLICT (id) DO NOTHING` で冪等化
- 確認: 48件、`confirmed_effects` 空が8件、STEP 1 の `aws-jp-179920-2` が入っている

所要: ツール呼び出し6回（DDL 1、INSERT 4、確認 1）。修正なし。

気づき（台本に効く）:
- **48件を SQL リテラルで流すと約50KB の出力になる**。当日 AI にこれを生成させると、出力トークンで数分かかるうえ、日本語の引用符エスケープで落ちる余地がある。AI に任せると「テーブルは MCP で作り、投入は `catalog/` を読む短いスクリプトを書く」と判断する可能性が高く、その方が速い。発話を「テーブル作成と件数確認は MCP で。投入の仕方は任せる」に緩めるか、「MCP だけで入れて」と縛って遅さも見せるか、どちらを見せたいかで決める
- 発話に「重複しても壊れないように」を入れないと `ON CONFLICT` が付かず、2回目の実行で主キー違反になる。リハーサルの繰り返しでは `scripts/reset.sh` でテーブルごと落とすので実害はないが、当日 STEP 1 をやり直した場合に踏む
- DDL を AI に任せると `confirmed_at` が text になる可能性がある。`docs/case-schema.md` に「`confirmed_at` は date」と書いてあるので、発話でスキーマ文書を指していれば防げる（今回は防げた）

気づき:

- `pkill -f` でプロセスを止めようとして自分のシェルを落とした。PID か `ss -ltnp` からの特定で止める
