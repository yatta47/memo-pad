## Q7. AIまわりの「〇〇エンジニアリング」の変遷

> プロンプト→ハーネス→ループ→グラフエンジニアリング…的な流れ

### 答え

**扱う範囲がだんだん外側に広がってきた、というのが流れです。** ただし「新しいものが古いものを置き換えた」わけではありません。**今もすべての層が同時に必要**です。

| 層 | 何を設計するか | 例えると | 典型的な症状（この層を直すサイン） |
|---|---|---|---|
| Prompt | 1回の指示の書き方 | 口頭での頼み方 | 意図と違う回答が返る |
| Context | 何を読ませるか（資料・履歴・ルール） | 渡す資料一式 | 前提を忘れる、知らないことを捏造する |
| Harness | ツール・権限・手順・検証をまとめた作業環境 | 作業場と道具と作業手順書 | 作業漏れ、やってはいけない操作をする |
| Loop | 繰り返して品質を上げる仕組み（作る→確かめる→直す） | レビューと手戻りの回し方 | 品質が安定しない |
| Graph | 複数の仕事を分岐・並列・合流させる構造 | 部署をまたいだ業務フロー | 大きなタスクが途中で崩れる、1か所の詰まりで全部止まる |

### 話すときのポイント

- **「進化の段階」ではなく「症状から選ぶ診断表」として紹介する。** 回答が意図とずれるならPromptを、作業が漏れるならHarnessを直す。いきなりGraphから組むのは典型的な失敗です（1モデルとツール2つで済む仕事に、エージェント7つを組んでしまう）。
- **ループとグラフは別の軸です。** ループは時間軸（同じ仕事を繰り返す）、グラフは構造軸（違う仕事を並べる）。グラフの中にループを入れることもあります。
- なぜこの順に広がったか: ①コンテキストウィンドウ（一度に読める量）が狭かった時代は、指示の書き方が勝負だった → ②読める量が増え、ツール呼び出しやRAGで「何を読ませるか」が勝負になった → ③長時間の作業を任せるようになり、「完了していないのに完了と言う」「勝手な操作をする」といった問題が出て、環境ごと設計する必要が出てきた。
- **注意点:** 「Loop Engineering」は2026年6月頃、「Graph Engineering」は2026年7〜8月頃にSNSで広まった言葉です。呼び名としてはまだ固まっていません。**名前を覚えるより、各層が何を解決するかを持ち帰ってもらう**ほうが価値があります。

## Q2. AIの推論の仕組み、ハーネスやループの具体的な実態

### 答え（推論の仕組み）

初学者に最低限伝えたいのは次の4点です。

1. **LLMは「次に来る単語（トークン）を1つずつ予測する」ことを繰り返しているだけ。** 知識を検索しているのではなく、学習したパターンから「もっともらしい続き」を出しています。**ハルシネーション（もっともらしい嘘）は故障ではなく、この仕組みの自然な副作用**です。
2. **モデルは会話を記憶していない（ステートレス）。** 2往復目でも、過去のやりとりを毎回すべて読み直しています。「前に言ったことを忘れる」のは、読み直す量が限界（コンテキストウィンドウ）を超えたり、長すぎて注意が散ったりするためです。
3. **「考えるモデル」（推論モデル、extended thinking）は、答える前に下書きの思考トークンを出してから回答する。** 仕組みは同じ次トークン予測で、「考える分のトークンを先に使う」ことで精度を上げています。そのぶん遅く、コストも高くなります。
4. **モデルは自分では何も実行できない。** ツール呼び出しとは、モデルが「このコマンドを実行したい」というテキスト（JSON）を出し、**周りのプログラムが実際に実行して結果を返す**仕組みです。

### 答え（ハーネスとループの実態）

4点目がそのまま「ハーネスとは何か」の答えになります。

```
while (まだ終わっていない) {
  応答 = LLM(システムプロンプト + 会話履歴 + ツール結果)
  if (応答がツール呼び出し) {
    権限チェック → 実行 → 結果を履歴に追加    ← ここがハーネス
  } else {
    終了（または検証へ）
  }
}
```

- **ハーネス** = このwhile文と、その周りにあるもの一式。**どのツールを渡すか、何を許可するか、何を読ませるか（CLAUDE.md、ルール、スキル）、いつ止めるか**を決めます。Claude CodeやCodex CLIは「ハーネスという製品」です。
- **ループエンジニアリング** = このwhile文を1段外側でも設計すること。「作る担当」と「確かめる担当」を分け、合格するまで回す。**止める条件（回数上限・コスト上限・時間上限・人間に渡す条件）を必ず決める**のが核心です。
- 実感してもらうための数字: 同じモデルでもハーネスを変えるだけで、ベンチマークの成功率が52%から76%まで変わったという報告があります（Harness Bench）。**「どのモデルを使うか」と同じくらい「どういう環境で動かすか」が効く**、というのが2026年の共通認識です。

### 話すときのポイント

- Claude Codeの画面で「ツール呼び出し→結果→次の判断」が流れる様子を見せると一発で伝わります。
- 「AIが勝手に判断して動いている」ではなく、「**AIが出した提案を、ハーネスが許可の範囲で実行している**」と言い換えると、後半のセキュリティの話（Q4）につなげやすくなります。

## Q1. ループエンジニアリング、自走。Databricksは良いと思った

### 答え

**自走（人間が毎回指示しなくても仕事が進む状態）に必要なのは、賢いモデルよりも「自分で合否を判定できる仕組み」です。**

ループの最小構成は次の3つです。

| 役割 | 何をするか | 失敗するとどうなるか |
|---|---|---|
| 作る担当（Generator / Maker） | 成果物を作る | — |
| 確かめる担当（Verifier / Checker） | 合格基準と照らして判定し、**具体的な直し方**を返す | 自分で自分を採点すると、甘くなって回っても良くならない |
| 止める仕組み（Manager） | 回数・コスト・時間の上限、人間に渡す条件 | 無限にリトライしてお金が溶ける |

押さえておきたい事実が2つあります。

- **確かめる担当は、作る担当とは別のコンテキストに置く。** 同じ会話の中で「見直して」と頼むのは自己採点になります。RefineBench（KAIST・CMU・NVIDIA、arXiv:2511.22173）では、自分で直すだけでは5回試しても正答率がほぼ横ばい、他のAIから具体的なフィードバックをもらうと5ターンでほぼ満点、という結果が出ています。
- **合格基準は、できるだけ機械で判定できるものにする。** テストが通る、lintが通る、スキーマに合っている、など。LLMに採点させる場合も、採点基準（ルーブリック）を明文化して渡します。「完了した」というAIの申告は主張であって、証明ではありません。

### Databricksについて

「良いと思った」の理由はおそらく、**ループを回すために必要な周辺機能が1つの基盤にそろっている**点だと思います。

- MLflow 3のトレーシング（エージェントが何をしたかの記録）と評価（Retrieval Groundedness＝回答が検索結果に基づいているか、Correctnessなどの採点器）
- Unity Catalogによるデータとモデルの権限管理・系譜管理
- 評価ゲート（スコアが基準未満なら自動停止）→ 人間の承認 → デプロイ、というCI/CDをコードで組める

つまり、**「確かめる」「記録する」「止める」を自前で作らなくてよい**のが強みです。一方、データ基盤がDatabricksにない組織では導入の重さが先に立ちます。**「Databricksだからできる」のではなく「この3機能が必要」と理解しておけば、ほかの基盤（Langfuse＋自前CI、Bedrock AgentCoreなど）でも同じ設計ができます。**

※ 質問者がDatabricksのどの機能（Agent Bricks、評価、データとの一体性など）を評価したのかは、当日に確認したいところです。

## Q6. ループやハーネスの設計、個人利用ではなくチームでの活用

### 答え

**個人利用とチーム利用の違いは「暗黙知をファイルとルールに出せるか」です。** 個人なら頭の中にある前提を、チームではリポジトリに置く必要があります。

| 観点 | 個人 | チーム |
|---|---|---|
| ルール・前提 | 自分の頭の中 | リポジトリのCLAUDE.md / AGENTS.md、rules、スキルとしてGit管理 |
| 変更 | 気が向いたら直す | PRでレビューして直す（ハーネス自体もコードとして扱う） |
| 権限 | 自分の判断 | 許可するコマンド・MCPサーバー・触ってよい環境を設定ファイルで統一 |
| 品質の担保 | 自分で見る | 機械ゲート（テスト・lint）＋リスクに応じた人間レビュー |
| コスト | 自分の財布 | 上限と見える化の仕組みが必要 |

### 実践のポイント

1. **ルールファイルは短く保つ。** 1行ずつ「これを消したらAIはミスをするか？」と問い、ミスしない行は消します。長いルールは全員分のコストになり、AIの注意も散ります。
2. **ハーネスの変更もPRにする。** プロンプトやスキルを変えたら挙動が変わるので、アプリのコードと同じようにレビューと履歴管理の対象にします。
3. **コストは「厳しく制限して申請制」より「低めに始めて自動で段階的に上げる」ほうが機能したという事例があります**（2026年8月の勉強会で、エンジニア約60名の会社が発表。申請制にすると遠慮して手が止まる）。
4. **並列で動かすなら作業場所を分ける。** 複数のエージェントや人が同じ作業ディレクトリを触ると衝突します。git worktree等で分けます。
5. **「誰が着手中か」を見える化する。** 自動ジョブと人間が同じチケットに同時に着手する事故は、実際によく起きます。

### 話すときのポイント

- 「チームでAIを使う」は「**チームでハーネスを保守する**」と言い換えられる、とまとめると伝わりやすいです。

## Q3. モニタリング

### 答え

**AIアプリのモニタリングは「普通のWebアプリの監視」に「中身の品質評価」を足したものです。** 普通の監視だけでは、**エラーなく、速く、自信満々に間違った答えを返している状態**に気づけません。

| 見るもの | 何を測るか | 既存監視との対応 |
|---|---|---|
| 動作 | レイテンシ、エラー率、タイムアウト | 従来のAPM |
| コスト | トークン数、1リクエストあたりの金額、利用者別の使用量 | クラウド費用の監視 |
| 過程（トレース） | どのツールをどの順で呼んだか、何を検索して何が返ったか | 分散トレーシング |
| 品質 | 回答が根拠に基づいているか、正しいか、ユーザー評価 | SLI/SLO（ただし定義が難しい） |
| 安全 | プロンプトインジェクションの兆候、機密情報の出力 | セキュリティ監視 |

### ポイント

- **最終回答だけでなく過程（トラジェクトリ）を記録する。** 「答えは合っていたが、無駄なツール呼び出しを20回していた」は、最終出力だけ見ても分かりません。
- **評価は2種類ある。**
  - デプロイ前（オフライン）: 質問と期待する答えのセットで、変更のたびに回帰テストする。プロンプトやモデルを変えたら必ず回す
  - 本番（オンライン）: 実トラフィックの一部をLLMに採点させ、品質の劣化（ドリフト）を検知する
- **コスト削減の効果は「量・質・コスト」の3軸で見る。** 安いモデルに切り替えてコストが下がっても、品質が落ちているだけかもしれません。
- 代表的なツール: Langfuse（OSS、セルフホスト可）、LangSmith、MLflow（Databricks）、Arize Phoenix、各クラウドのマネージド機能。OpenTelemetryのGenAIセマンティック規約に寄せておくと、ツールを乗り換えやすくなります。

## Q4（前半）・Q9. RAGと検索／独自ナレッジ（コンテキスト）の蓄積

> Q9: 通常の生成AIが学習していないデータ

### 答え

**社内の独自知識は「学習させる」のではなく「その場で読ませる」のが基本です。** その代表的な方法がRAG（検索して、見つけた資料をコンテキストに入れて回答させる）です。

判断の目安は「**A4一枚のメモを渡せば、入社初日の人でもできるか？**」。

| | 知識（What） | 振る舞い・形式（How） |
|---|---|---|
| 例 | 規程、製品仕様、過去の障害対応、顧客情報 | 報告書の型、文体、判断の癖 |
| 更新頻度 | 頻繁に変わる | あまり変わらない |
| 手段 | **RAG / ファイルで渡す** | プロンプト → それでも駄目ならファインチューニング |

ファインチューニングで知識を入れるのが悪手な理由:

1. うろ覚えのまま、もっともらしく答える（ハルシネーションが減らない）
2. **間違いや古い情報を後から消せない**
3. 出典を示せない

### RAGで実際につまずくところ

**RAGのトラブルの大半は、モデルではなく検索が原因です。** 本棚に正しい資料があっても、引けなければ答えられません。

- **資料の質がすべて。** 古い資料、矛盾する資料、「最新版」が複数ある状態では、AIも混乱します。**ナレッジ蓄積の本当の仕事は、AI導入ではなくドキュメントの棚卸し**です。
- **検索方法を組み合わせる。** ベクトル検索（意味が近い文書）だけでは、型番やエラーコードのような完全一致に弱いです。キーワード検索（BM25）と組み合わせるハイブリッド検索が標準です。
- **関係をたどる質問にはGraphRAG。** 「このサプライヤーが止まったら、どの顧客に影響するか」のように複数の情報をまたいでたどる質問は、普通のRAGが苦手です。ナレッジグラフを併用します。ただし構築と保守は重いので、必要になってから検討します。
- **評価する。** 「必要な資料を検索できたか」と「回答が検索結果に基づいているか」を分けて測ります（Q3参照）。

### 2026年の実務的な選択肢（軽い順）

1. **ファイルで渡す**: CLAUDE.md、スキル（Markdownの手順書）、リポジトリ内のドキュメント。エージェントが自分でgrepして読む。**小〜中規模ならまずこれで十分**
2. **MCP経由で既存システムを検索させる**: Confluence、社内Wiki、チケットシステムなど
3. **本格的なRAG基盤**: ベクトルDB＋ハイブリッド検索＋評価。大量の文書、権限管理、複数アプリで共用する場合

### 蓄積を「育てる」には

- 一度作って終わりにしない。**AIが答えられなかった質問・間違えた質問を記録し、その穴を埋める資料を足す**ループを回す（Q1のループの考え方と同じ）
- 資料に更新日・担当者・有効期限を持たせ、古い資料を検索対象から外す
- 権限を考慮する: 本人が見られない資料をRAG経由で見られてしまう事故を防ぐため、検索時に権限でフィルタする

## Q5・Q4（後半）. AIツール／Webサービスとの連携の現状と将来性、AIとセキュリティ

### 答え（連携の現状）

**連携手段は、ほぼMCP（Model Context Protocol）に標準化されました。** MCPは「AIとツールをつなぐUSB規格」のようなもので、一度MCPサーバーを作れば、Claude、ChatGPT、Cursor、Codexなど複数のAIから使えます。

| 手段 | 向いている用途 |
|---|---|
| MCP | 外部サービスの読み書き（GitHub、Slack、Confluence、DB、クラウド） |
| CLI・API直叩き | エージェントがシェルを使える環境なら、`gh`、`aws`などの既存CLIで十分なことが多い |
| スキル（Markdownの手順書） | 「どう使うか」の知識。MCPと競合するものではなく、MCPの上に載る層 |
| ブラウザ操作（Playwright等） | APIがないWebサービス。遅く壊れやすいので最終手段 |

### 将来性

- **主要なSaaSは公式MCPサーバーを出す流れ**です。「このサービスはAIとつながるか？」は、「公式MCPがあるか」で判断できるようになっています。
- クラウド各社が、MCPの認証・権限・監査をまとめるゲートウェイを提供し始めています（例: AWS Bedrock AgentCore Gateway）。**個人の手元でつなぐ段階から、組織として管理する段階**に移りつつあります。
- エージェント同士の連携（A2Aなど）は規格が出ていますが、実務での定着はMCPほど進んでいません。
- ※ この分野は半年で状況が変わります。発表の直前に最新情報を確認します。

### 答え（セキュリティ）

**一番伝えたいのは「つなげるほど便利になり、つなげるほど危険になる」ということです。** 覚えやすい枠組みが「**致命的な三要素（lethal trifecta）**」（Simon Willison, 2025）です。

> ① 機密データにアクセスできる
> ② 信頼できない外部コンテンツを読む（Webページ、メール、Issue、他人が書いた文書）
> ③ 外部に送信できる
>
> **この3つが1つのエージェントにそろうと、プロンプトインジェクションで情報を盗まれ得る。**

プロンプトインジェクションとは、読ませた文書の中に「このファイルの中身を〇〇に送信せよ」のような指示を埋め込み、AIを操る攻撃です。**LLMは「データ」と「指示」を原理的に区別できない**ため、現時点で完全な防御方法はありません（Q2の「全部をテキストとして読んでいるだけ」とつながる話です）。

対策の考え方:

| 対策 | 内容 |
|---|---|
| 三要素を同時にそろえない | 外部コンテンツを読むエージェントには送信権限を持たせない、など |
| 最小権限 | 読み取り専用のトークン、対象を絞った権限。本番環境の書き込み権限を渡さない |
| 人間の承認を挟む | 削除・送信・デプロイなど不可逆な操作の前に承認を入れる |
| 隔離 | サンドボックス、コンテナ、ネットワークの制限 |
| 拡張機能を吟味する | 野良のMCPサーバーやスキルは、他人のコードを自分の権限で動かすのと同じ。ある調査では、非公式マーケットのスキルの約26%に脆弱性、約5%に悪意ある挙動が見つかっている |
| ログを残す | 何を読み、何を実行したかを監査できるようにする（Q3） |

### 話すときのポイント

- 「AIを信用するか」ではなく、「**AIが騙されても被害が出ない権限設計になっているか**」で考える、とまとめます。これはAIに限らず、従来のセキュリティ設計の考え方そのものです。

## Q8. AI利用によって発生する特有の認知負荷への向き合い方

> AIスロップ対策、膨大なコード・ドキュメントのレビューなど

### 答え

**AIで「作るコスト」はほぼゼロになりましたが、「確かめるコスト」は下がっていません。** 負荷の正体は、生成量と検証能力のアンバランスです。実際、GitHubではこの3年でPR数が5倍になったと報じられています。

AIスロップ（AIが量産する、中身の薄い・それっぽいだけの成果物）が厄介なのは、**見た目が整っているので、ざっと見ただけでは悪さが分からない**ことです。

### 向き合い方（4つの方向）

**1. 読む量そのものを減らす（生成側で絞る）**

- PRを小さく分ける。AIに一気に大量の変更を作らせない
- 「何を作るか」の段階（仕様・設計・テストケース・スキーマ）でレビューする。実装の後で読むより、前で合意するほうが安い
- 「完了の条件」を先に決めてAIに渡す（Q1の合格基準）

**2. 機械で判定できることは人間が見ない**

- テスト、lint、型チェック、スキーマ検証はCIに任せる
- 人間は「機械では判定できないこと」（設計の妥当性、要件との整合、読みやすさ）に集中する

**3. リスクで仕分ける（トリアージ）**

- 低リスクな変更はAIレビューと機械ゲートだけで通し、高リスクな変更（認証、課金、データ削除、インフラ）だけ人間が必ず見る。AnthropicやOpenAIもこの方式だと報じられています
- **AIレビューの落とし穴**: 指摘が増えて、「その指摘が正しいか」を確かめる仕事がむしろ増えることがあります。ある事例では69件中52%が「重大な指摘なし」だったのに、そのレビュー本文は平均2,737字ありました。**時間を奪うのは調べることではなく、「もう見なくていい」と判断できないこと**です
- 対策として、AIに「見なくてよい」と判定させるなら、その根拠の強さを示させます（実行した証跡がある／全件確認した／一次資料の原文がある／推測だけ、など）。**推測だけの根拠では「見なくてよい」と言わせない**

**4. 人間側の姿勢**

- **分からないものはApproveしない。** 読んでも分からないコードは、AIが書いたかどうかに関係なく差し戻す理由になります。「もっと読みやすく書けないか」は有効な指摘です
- **説明できないものは出さない。** 自分がAIに作らせた成果物について、他人に聞かれて説明できないなら、まだ出す段階ではありません。AIスロップの一番の予防はこれです
- 文章の場合は「AIっぽい言い回し」を消すツールもありますが、やりすぎると別の不自然さが出ます。**中身（自分の判断・具体的な経験）があるかどうか**のほうが本質です

### 話すときのポイント

- この質問は「正解がまだない」分野だと正直に言います。各社が別々の方法を試している段階です。そのうえで「**生成を絞る／機械に任せる／リスクで仕分ける／説明責任を持つ**」の4方向を持ち帰ってもらいます。

1. **1枚につき、伝えたいことを1つ、図を1つ。** メモの表や箇条書きをすべて載せない。載せきれない内容は、話す内容と配布資料（このメモ）に回す

4. **数字には小さく出典を添える。** 数字が一人歩きしないようにする（出典は各質問の節に記載）
