## 1. 独自ナレッジの分類

分類軸は「その知識はどこに書いてあるか、あるいは書いていないか」。LLMに渡す前提ではこの軸が一番実用的。

| # | 種類 | 例 | LLMへの渡し方 |
|---|---|---|---|
| 1 | 文書として存在する知識 | システム構成、API仕様、運用手順、障害記録、議事録、法規制、業界標準 | RAGの得意領域。検索して渡す |
| 2 | 文書にはないが人の頭にある知識（聞けば言語化できる） | 暗黙の判断基準、社内用語の定義、地雷の位置、「なぜそうなっているか」 | 言語化して文書にする工程が先。「A4一枚で済むか」の判断がここで効く |
| 3 | 言語化しにくい知識（本人も説明できない） | 文化・空気、スタイルや好み、勘・パターン認識 | RAGでは扱いにくい。まず言語化できる部分を切り出して2に落とす。残りはFTか実例提示 |
| 4 | 知識ではなく「状態」 | 今週の当番、進行中案件、直近リリース、現在のアラート | 溜めない。ツール（API・DB・チケット）から都度引く。RAGに入れると古い状態を答える |

判断は「文書があるか → 書けるか → 書けないか → そもそも状態か」の順で下りる。業種の慣例は1、文化は3、開発の独自ナレッジは1と2に散らばる。この散らばり方自体が「独自ナレッジ」を一枚岩に扱えない理由。

## 2. 2と3の溜め方: 「書いてもらう」ではなく「使われた瞬間に拾う」

「ナレッジを書き出してください」はほぼ確実に失敗する。本人が何を知っているか自覚していないため。

### 暗黙知が表に出る5つの瞬間

- **質問された時**: Slackで「これどうすれば」に答えた返信
- **訂正した時**: PRレビューの「ここはこうじゃなくて」、新人の作業への口出し
- **判断した時**: 「今回はAで行く、理由は」の一言
- **驚いた時**: 新人や外部の人の「なんでこうなってるんですか」。本人には当たり前すぎて見えないものが外の目で浮く
- **失敗した時**: 障害振り返りの「実はあれは触っちゃいけなかった」

収集はこの5場面のログを捕まえる設計になる。

### 抽出はAI、承認は人

```
Slack / PRレビュー / 会議文字起こし
  → LLMが「判断ルールの候補」を抽出（「〜のときは〜する、理由は〜」の形に）
  → 専門家は候補を見て ✓ / ✗ / 修正 だけ返す
  → ✓ が付いたものだけナレッジとして登録
```

専門家の負荷を「書く」から「判定する」に落とすのが要点。判定の過程で「正確にはこう」という追加の暗黙知が出る。

### 3を2に落とす道具としてのAI

AIに一度やらせて、直された箇所を記録する。人間は自分の常識を説明できないが、他人の間違いは指摘できる。AIを「常識を知らない新人」として使い、差分と「なぜ直したか」の一言を集める。このリポジトリのfeedback memoryはこの構造。

### 記録の形式

「ルール文」ではなく「判断の記録」で溜める。

- 状況（どんな時に）
- 判断（何をしたか）
- 理由（なぜか）
- 出典（誰が、いつ、どのスレッドで）
- 有効期限か見直し条件

理由と出典があれば後で「もう古い」と判定できる。ルール文だけだと、なぜか分からないまま守られ続けるか無視されるかのどちらか。

### やってはいけないこと

- ナレッジ書き出しキャンペーン（出るのは1だけ）
- 誰も見ないWikiを先に作る（使う場面がないと溜まらない。先に「困ったらここに聞く」入口を作り答えを溜める）
- 全部を溜める（3割はルールに落ちる。残りは「この件は○○さんに聞く」のルーティング情報として残す）

### 平たく言えば「会話からマイクロADRを掘る」

普通のADRとの違いは2点。

- **粒度がずっと小さい**: 「この顧客には先に電話」「このディレクトリは触らない」の1行。ADRを書くつもりで構えると重くて続かない
- **起点が逆**: ADRは判断者が「残す」と決めて書く。ここでは本人が記録に値すると思っていない判断を、会話から拾って承認だけしてもらう

## 3. 拾えない残余は必ずある

「会話をAIが見て推測し、人が承認する」構造では、根本的に拾えないものが残る。100%を取りに行く設計は壊れる。

### 拾えないもの

1. **会話に出てこない知識**: 判断が頭の中で完結して行動にしかならない。ログに無いものは拾えない
2. **文脈が欠けているもの**: 「いつもので」「あれはやめとこう」。AIが推測を埋めると、もっともらしい嘘のルールが生まれる。拾えないより悪い
3. **ルールの形を拒むもの**: 「そうとも限らない」としか言えないもの。実態はパターン認識
4. **拾ってはいけないもの**: 人間関係、政治。文書化した瞬間に害になる
5. **拾った瞬間から古くなるもの**

### 推測ステップ自体の危険

n=1の判断をルールに昇格させる事故が一番起きやすい。対策は「同じ候補が2回以上、別の場面で出てから昇格」。このリポジトリの「環境の癖は複数回の実害を確認してからmemoryに書く」と同じルール。

### 残余の扱い

- 目標を8割に置く。狙いは「同じ質問が繰り返される回数を減らす」であって完全な外部化ではない
- 拾えないものは「誰が知っているか」に変換する。入口は取れる
- 拾えなかったものを可視化する。同じ質問が何度も来る、AIが同じ箇所で何度も直される、という記録は「まだ拾えていない暗黙知の地図」。聞き取りは高コストなので、この地図で絞ってから行く
- 3は「ルール化」を諦めて「実例の蓄積」にする。AIには似た実例を提示させるだけで、ルールを合成しない

結果として「会話からADRを掘る」主経路の横に、「誰に聞くかの台帳」と「まだ拾えていない領域の地図」を並走させる3本立てになる。

## 4. 世の中の取り組み（2026-09時点）

### 会話ログ起点の4つの流れ

| 流れ | 代表 | 狙う層 | 所見 |
|---|---|---|---|
| Slack起点の回答キャプチャ（SaaS） | Question Base、Slack Agentforce、Glean、Guru | 「質問された時」経路の製品化 | 商品として成立。ただし実態は1と2の浅い部分 |
| 日本の製造業「暗黙知の形式知化」 | NTTデータ×川崎重工、KPMG「暗黙知の形式知化エージェント」（2026-01）、GENIAC-PRIZE（58件応募）、匠和会（2026-03） | 3（熟練技能: 釜炊き、西陣織、鋳造、PLCラダー） | インタビュー＋作業映像をLLMで構造化。高コスト。日経xTECH「学ばせただけでは形式知にならない」はn=1警告と同じ |
| 開発者向けエージェント学習ルール | CLAUDE.md / auto-memory、Cursor Rules、AGENTS.md | 「訂正した時」経路の開発者版 | 個人〜チーム規模。組織横断の承認・矛盾解消は未整備 |
| 学術: 自己進化するエージェント記憶 | Reflexion、ExpeL、Memory-R1、SSGM | 経験→教訓抽出→記憶→次の行動のループ | SSGMのように「進化する記憶のガバナンス」を扱う論文が出始めた |

どの流れも「拾えない残余」を明示的には扱っていない。空いているのは「承認・矛盾解消・失効」の統制で、構造的にはデータガバナンスと同じ問題。

### 会話ログに限らない7系統

| 系統 | やり方 | 代表 | 溜まるもの |
|---|---|---|---|
| 1. 既存文書をそのまま繋ぐ | コネクタを刺してRAG。蓄積は既存ツール任せ | Glean、Microsoft Copilot、Atlassian Rovo、Onyx（OSS） | 分類1。一番普及。ゴミも一緒に繋がる |
| 2. AIが編纂するWiki | 生文書に毎回RAGせず、AIが一度読んで実体・概念・矛盾・相互リンクのMarkdown Wikiに編纂し、以後Wikiに聞く | Karpathy「llm-wiki」（2026-04、2週間で5,000スター）、DeepWiki | 1と2。質問のたびにWikiが育つ「複利」 |
| 3. 業務プロセスの出口から拾う | 障害振り返り→ランブック、チケット→FAQ、PRレビュー→ルール、会議録→決定ログ | incident.io、Zendesk/Intercom Fin、CLAUDE.md、Gong/tl;dv | 2。会話ログはこの一部 |
| 4. 構造化して溜める | ナレッジグラフ、オントロジー、セマンティックレイヤーで「定義と関係」を持つ | Palantir Ontology、Neo4j GraphRAG、dbt Semantic Layer、Atlan | 「この会社で売上とは何か」という定義の知識 |
| 5. 人から引き出す | 熟練者インタビュー、作業映像の構造化 | NTTデータ、KPMG | 3。高コストで対象を絞る |
| 6. エージェント記憶基盤 | アプリが動くうちに利用者ごとの記憶を自動で溜める | Mem0、Letta、Zep/Graphiti | 個人の文脈と好み。組織知より個人知 |
| 7. モデルに焼く | ファインチューニング、継続事前学習 | 業種特化モデル | 振る舞いと文体。知識用途では減っている |

### 2026年に目立つ3つの動き

- **「生RAG」から「編纂済み」へ**: llm-wikiが火をつけた。このリポジトリのknowledge/wikiは同型
- **定義の再評価**: Gartnerが2026年上位トレンドにセマンティックレイヤーとGraphRAG。dbtベンチマークでセマンティックレイヤー有り98.2%、素のText-to-SQL 90%。データカタログ構想に直結
- **構造化は難しい**: 企業ナレッジグラフをパイロットから先に進められた企業は15%未満。エンティティ解決とオントロジーのバージョン管理で止まる

入口は出揃っていて、差が出るのは「編纂」と「統制」。

## 5. 個人と会社で何が変わるか

難しさの正体は規模ではなく、個人では自明だった前提が会社で崩れること。

| 前提 | 個人 | 会社 |
|---|---|---|
| 正しいかの判定者 | 自分1人 | 部署ごとに正解が違い、最終判定者が決まっていない |
| 溜める人と使う人 | 同一人物。動機がある | 別人。溜める側にコストだけ、便益は他人へ |
| 古くなったと気づく人 | 自分の違和感 | 誰も気づかない。書いた人はもういない |
| 見てよい範囲 | 全部 | 権限、秘密、人事情報。溜めた瞬間に漏洩経路になる |
| 間違いの責任 | 自分で被る | 「AIが言った」で誰の責任でもなくなる |
| 溜めない自由 | ない | ある。溜めなくても本人は困らない |

### 足場になる観察

- 会社の中にも「個人レベルならどうにかなる」範囲がある。1人がオーナーで、1つの領域で、使う人と溜める人が近い場所。会社Cursor構想はそこを狙っている
- 「同じことを何度も聞かれる」問題（2026-09-11の議論）は、聞かれる側が溜める動機と判定者を兼ねるので、上の表の右列を一時的に回避している。最初の足場として理にかなう
- 全社の統制は先に設計しない。先に作ると溜まる前に手続きが重くなる。個人規模のものを2つ3つ横に並べて衝突した事例に対して後付けするほうが現実に合う

「会社の独自ナレッジ蓄積」を一つの問題として解くと見えなくなる。「個人規模で回るものを増やして、衝突したところだけ統制する」の順にすると見えている範囲だけで進められる。8割の再現性と持続性の判断軸では、前者は一発の大設計、後者が続く仕組み。

## 6. 着地: 雑多に溜めて、成長させ、正本として維持する統制を後から掛ける

方針: 雑多な文章でもよいから既定の場所にAIが読めるデジタルデータで溜め、そこを成長させるのを基本にし、その過程で正本として維持できるよう統制を掛けていく。

### 「雑多でよい」のは中身。来歴は最初から付ける

後から統制を掛けられるかはここで決まる。書く側のコストはほぼゼロ（ファイル名とフロントマター）。

- 誰が書いたか（または誰の発言から拾ったか）
- いつ書いたか
- 出典（Slackスレッド、チケット番号、会議名など辿れるもの）
- 状態（雑記 / 確認済み / 正本 / 失効）

これが無いと「正しいか」「古いか」「誰に聞けば分かるか」が全部判定不能になり、雑多な山がゴミの山に変わる。

### 正本への昇格は「使われたとき」に起こす

- 同じ雑記が2回以上参照された
- AIが回答の根拠として引いて、人が正しいと確認した
- 誰かが「これ違う」と訂正した（訂正された瞬間が正本にする価値の証拠）

引き金が起きたものだけ正本に上げ、それ以外は雑記のまま放置してよい。「放置してよい」を明示しないと全部を整理しようとして止まる。

### 構造は2層で足りる

```
raw/       雑多に溜める。誰でも、何でも、来歴付きで
curated/   正本。昇格の引き金を通ったものだけ。オーナーがいる
```

このリポジトリのideas/とknowledge/wikiの関係と同じ。個人で回っている型をそのまま会社に持ち込む。

### 統制が要る箇所は当面3点だけ

- curatedに誰が入れられるか
- curatedの各項目にオーナー（更新責任者）がいるか
- 失効の判定（オーナー不在で自動的に「要確認」に落とす等）

これ以外は衝突や事故が実際に起きてから足す。
