Nginx 499 ベースライン調査キット

「大量の499は問題ない」を証明して閉じるための1枚 — 観測事実: request_time ≒ upstream_response_time / 値はバラバラ(0.13s〜3s) / EC2:ECS 50:50 で均等発生 / ユーザー影響報告なし
Done の定義 代表的な499を1件取り出し、そのリクエストの一生（誰が・どのパスに・何秒待って・なぜ切ったか）を語れること。＋ ベースライン文書化 ＋ 499率の逸脱アラート

1着地のストーリー

消去法で確定済み
  • コア数 (2core/1core 両方で発生)
  • ECS / Fargate 固有 (EC2でも均等発生)
  • Nginx設定差・KeepAlive (両系統同率)
  • ALB自身の再送 (送信済みリクエストは再送しない仕様)

→ 原因・再送者とも ALBより手前のクライアント か 両系統共有の依存先

仮説A: 短時間群 = プログラムの正常キャンセル

検索の打鍵ごとのabort / SPA画面遷移 / ポーリング世代交代。仕様として文書化して閉じる

仮説B: 長時間群 = 遅さによるサイレント離脱

成功時p95を超えて待った末の切断。499問題ではなく該当パスのレイテンシ問題に変換して改善バックログへ

率の確定→ 2群分割→ 顔ぶれ特定→ 個体解剖→ 文書化+監視

2必要な情報

Nginx アクセスログ（log_format 仕込み）

status / method / path / User-Agent に加えて:

rt=$request_time uct=$upstream_connect_time
uht=$upstream_header_time urt=$upstream_response_time
ust=$upstream_status trace="$http_x_amzn_trace_id"
ALB アクセスログ (S3 + Athena)

elb_status_code (460?) / target_status_code / target_processing_time / client:port / trace_id
trace_id: 無→ALBがRoot生成 / 有→Self追記でRoot保持。Nginx↔ALBの同一試行を1対1で突合（リトライ間は別Root。前段付与なら同一→再送即確定）

成功リクエストのレイテンシ分布

パス別 p50 / p95 — 短時間群と長時間群を割る分類閾値に使う

前段の構成情報（ヒアリング）

ALBの手前は誰か（ブラウザ直 / API GW / 他システム）と、そのtimeout・retry設定。0.13秒切断の正体はここで確定

3クエリ Nginx=Logs Insights / ALB=Athena ※parseはログ形式に合わせ調整

Q1 499率と分布 — 全体像を1つの数字に

stats count(*) as total, sum(status=499) as c499,
  c499*100.0/total as pct by bin(1h)

Q2 2群分割・顔ぶれ — path/method/UA別 上位

filter status=499 | stats count(*) as n,
  pct(request_time,95) by path, method, user_agent | sort n desc

Q3 分類閾値 — 成功時のパス別 p50/p95

filter status<400
| stats pct(request_time,50), pct(request_time,95) by path

Q4 ALB側突合 — 460と切断者の特定 (Athena)

SELECT time, elb_status_code, target_processing_time,
  client_ip, request_url, trace_id FROM alb_logs
WHERE elb_status_code = 460 AND day = '...' ORDER BY time

Q5 個体解剖 — 同一クライアントの直後再送パターン

SELECT * FROM alb_logs WHERE client_ip = '<Q4のIP>'
  AND time BETWEEN '<t-5s>' AND '<t+5s>' ORDER BY time
-- 判定: 数百ms内に同一URL再出現+ポート違い=新接続の
--  打ち直し(透過リトライ) / 同ポート=通常の連続アクセス
判定マトリクス
(Q5の再送パターンで裁く)
GET + 直後にパラメータ違い再送世代交代キャンセル（検索/ポーリング）。正常 → ベースライン文書化して閉じる
GET + 再送なし画面遷移・コンポーネント破棄。正常 → 同上
完全同一リクエストの即時再送再送側が200なら実害なしの「打ち直し」→ 増幅率を記録して閉じる。過剰(数十%超)なら前段のtimeout/retry設定へ
