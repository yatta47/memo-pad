ECS Container Insights の見方

雰囲気で眺めず、キャパシティ判断・異常検知・原因切り分けに使う。平均ではなく p95 / max / 再起動を軸に見る。
20%流量でMEM 60%は危険寄り 100%へ上げる前に、40%・60%で傾きを確認。比例に近いなら `2048 MiB` は不足濃厚。

1. 見る順番

1
Service 全体 CPUUtilized / MemoryUtilized / RunningTaskCount で全体の健康状態を見る。
2
Task 単位 平均に隠れた偏りを見る。特定タスクだけ高いならサイズ不足以外も疑う。
3
Container 単位 MyApp だけ重いのか、サイドカーも増えているのかを分ける。
4
Logs / ECS Events メモリ上昇時刻に OOM、再起動、特定API、バッチ、外部API遅延がないか突き合わせる。

2. CPU / MEM 判断軸

Memory は余白が重要

上限に近づくと OOM で落ちる。平均より p95 / max を見る。

<70%余裕あり
70-80%注意。流量増加時は要検証
>80%増強検討。max 90% は危険

CPU は遅延とセットで見る

CPU高だけでは即死しない。p95 latency / error rate と相関させる。

<60%余裕あり
60-80%注意。スパイク傾向を見る
>80%増強 or スケールアウト

3. カナリア時の判断表

20% traffic
MEM 60%
→
40% / 60% p95 / max / restart
で傾きを確認
観測結果 判断 次の一手
40%でMEM 75%超 2048 MiB不足濃厚 4096 MiBへ増強
60%でMEM 80%超 100%は危険 4096-8192 MiB検討
MEM低いがLatency悪化 CPU/DB/外部API疑い ALB/アプリ指標と相関
OOM / Restartあり 即対応 メモリ増強 + 原因ログ確認

4. 誤読しやすいポイント

平均だけで判断しない Service平均は偏りを隠す。p95 / max とタスク別の Top contributors を見る。
Memory 60%の意味は流量込み 100%流量時の余力を見る。20%で60%なら、増え方の傾きが判断材料。
5コンテナ同居はスケール単位に注意 MyAppだけ重いなら、タスク全体を太らせるより別Service化の方が安い場合がある。
Container Insights単体で完結しない ALBのRequestCount、TargetResponseTime、5XX、アプリログと必ず並べる。
CPU高とMEM高は意味が違う CPU高は遅延、MEM高はOOMに直結しやすい。対応の緊急度が違う。
最短ルール: 「Service平均 → Task偏り → Container原因 → Logs相関」。カナリア中は traffic / p95 / max / restart を表で見る。
