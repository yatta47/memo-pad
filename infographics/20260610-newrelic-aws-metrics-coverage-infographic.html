AWS × New Relic メトリクス連携の責任分界

CloudWatch Metric Streams と newrelic-infra（ECS統合）は競合する選択肢ではなく、観測している場所が違う。
Metric Streams = タスクの外側（AWSの外形観測の転送路）／ newrelic-infra = タスクの内側（エージェント直接実測・CloudWatch非経由）

観測エリアとデータ経路

🟠 タスクの外側 — CloudWatch 経由
AWSコントロールプレーンが発行する「外形観測」メトリクス。タスクの中身（コンテナ個別）はここには無い。
CloudWatch
AWS/ECS: Service / Cluster 粒度の CPUUtilization・MemoryUtilization（予約比 %）・runningCount ECS/ContainerInsights: Task 粒度の CpuUtilized / MemoryUtilized 等 ※別途有効化・追加課金 周辺サービス: ALB / API Gateway / MSK / Lambda / RDS … CloudWatch にある物すべて
▼CloudWatch Metric Streams（push・準リアルタイム）
Kinesis Data Firehose

設計上の急所

Nginx + アプリが同居するタスクでは、CloudWatch（Container Insights 含む）に出るのは Task 合算の値まで。 「どちらのコンテナが CPU / メモリを食っているか」を New Relic 上で分解できるのは newrelic-infra の ContainerSample だけ。 逆に ALB・API Gateway・MSK などタスクの外の世界は newrelic-infra からは見えず、Metric Streams（CloudWatch）が唯一の経路。両者は併用が前提。

比較表

観点 🟠 CloudWatch Metric Streams 🟢 newrelic-infra（ECS統合）
データ源 AWS が CloudWatch に発行した外形メトリクス エージェント自身の実測（タスクメタデータ / Docker API 由来）。CloudWatch 非経由
粒度 Service / Cluster（Container Insights 有効で Task まで）。コンテナ個別は不可 コンテナ個別＋クラスター単位（ContainerSample / EcsClusterSample）
カバー範囲 ECS 以外も含む CloudWatch 全ネームスペース（ALB / API GW / MSK / Lambda…） エージェントが居るクラスター / タスクの中だけ
レイテンシ 準リアルタイム（CW 発行は概ね1分解像度） 秒単位（エージェント直接収集）
デプロイ AWS 側設定のみ（Firehose + Stream）。タスク定義の変更不要。1リージョン1 sink 制約 EC2: daemon で全ノード一括。Fargate: 全タスク定義にサイドカー追記（運用コスト高）
コスト構造 CW Metric Streams + Firehose 転送課金（CW API コール課金は不要） エージェント無償・NR ingest 増加＋タスクの CPU / メモリを少し消費
役割分担の早見
・サービス全体の健全性・周辺リソース（ALB / MSK / API GW） → Metric Streams
・タスク内のコンテナ別リソース消費・秒単位の解像度 → newrelic-infra
・アプリ内部（レスポンスタイム・エラー・分散トレース） → APM 言語エージェント（infra と同居で相関表示）
・CloudTrail / Health / Trusted Advisor / X-Ray → API Polling（この4つだけは現状 Polling が唯一の手段）
