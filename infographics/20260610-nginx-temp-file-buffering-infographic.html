ADR: Nginx temporary file 警告の取り扱い

[warn] a client request body is buffered to a temporary file — 大容量ファイル送信API（約200件 × 10MB）で大量出力され、保守からの問い合わせが続いている件の意思決定記録
Status: Proposed（検証完了後 Accepted） Date: 2026-06-10 Scope: ECS Task内 Nginx / FireLens
決定（Decision） バッファリング設定は変更しない（temp file退避は正常動作として容認）。warnはFireLens（配送の根本1箇所）で除去し、理由を Runbook と設定コメントに固定する

1コンテキスト

事象

10MB級のbodyが client_body_buffer_size（デフォルト8k|16k）を超え、ディスク（temp file）へ退避。遅いクライアントからアプリを隔離する安全弁が働いた正常動作でありエラーではない

構成

ALB → Nginx → .NETアプリ（同一Task内 / Fargate vCPU 1024・メモリ 2048MB）。ログは FireLens 経由で New Relic と CloudWatch Logs の両方へ配送

何が問題か（技術ではなく運用）

技術的実害なし: 書込は200×10MB≒2GB、転送後削除。実害は保守からの問い合わせが止まらないこと。既知無害のwarnを流し続けると「warnは無視してよい」と学習され、意味のあるwarnまで読まれなくなる（アラート疲れ）

前提条件
  • client_max_body_size ≥ 10MB 設定済み（413が出ていない）
  • 大容量送信は正当な業務仕様である

2検討した選択肢

A. client_body_buffer_size 増量不採用

10MB×同時接続数をRAMに抱える。タスクメモリ2048MBを.NETと分け合う前提では成立しない（同時20件で200MB、200件で2GB）

B. proxy_request_buffering off（ストリーミング化）不採用
メリット
  • temp file書込ゼロ → warnも消える
  • 受信しながら処理開始できる
  • Nginxのメモリ/ディスク不使用
デメリット
  • 受信完了までアプリ接続を拘束
  • 1core .NETの同時処理枠を削る
  • 送信開始後は上流リトライ不可
  • 緩衝材を外しただけ

再考条件: 受信即処理の要件化 / ディスクI/O実測逼迫 → 該当locationのみ

C. location限定で error_log レベルをerrorに次点

Nginx設定だけで完結するが、同locationの他のwarn/noticeも消える

D. temp file容認 + FireLensで該当warnのみ除去採用

ファンアウト手前の1箇所で除去＝NR/CW両出口が常に一致。失う観測はこの1行だけ

3対処（実装と検証）

① FireLens（Fluent Bit）に grep フィルタ追加

# 既知warn除去: ファイル送信API(10MB級)の正常動作通知。
# 対処不要。経緯と説明は Runbook <リンク> 参照 (ADR 2026-06-10)
[FILTER]
    Name    grep
    Match   nginx-firelens-*
    Exclude log buffered to a temporary file

② 記録の固定（再質問の根本対策）

Runbookに1行「この警告はファイル送信APIの正常動作。対処不要」＋ 設定ファイル自体に上記コメント。ログを見ても・設定を見ても・Runbookを見ても同じ答えに辿り着く状態にする

③ 検証（ポジティブ・ネガティブ両方）

  • (a) 該当warnが NR と CW の両方から消えた
  • (b) 同じNginxの他のwarn/errorは引き続き届く
  • (c) マッチしない場合は正規表現のスペースを \s に置換
  • (d) Matchタグは必ずNginxコンテナに限定（アプリログの巻き添え防止）
帰結
(Consequences)
維持されるもの遅いクライアントからのアプリ保護（接続拘束時間の最小化）。1core .NETの同時処理枠を守る現行の挙動はそのまま
失うものディスク退避の発生をログでは観測できなくなる。必要ならエフェメラルストレージ使用率の監視で代替する
将来の地雷readonlyRootFilesystem 化すると temp file が書けず warn でなくエラーになる。読み取り専用化の際は temp path の volume マウントが必須
運用メモFireLens カスタム設定（config-file-type: S3/file）が未導入ならその仕込みが作業の大半。フィルタ追加後のデプロイはタスク定義の改訂で反映
