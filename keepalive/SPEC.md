## 1. 目的 / 背景

### 目的
会社PCの**無操作ロック（画面ロック → 再ログイン）**を、ユーザーが望むタイミングで延長する常駐アプリ。短時間離席（トイレ等）でロックされ、そのたびに再ログインが発生して生産性が落ちる問題への自衛策。

### なぜ「可視ウィンドウ」か（設計の核）
バックグラウンド常駐だと「効いているのか止まっているのか分からない」状態になり、ユーザーが一番避けたい不確実性を生む。そこで**アプリの動作状態と、信号を送っている事実を画面に出す**ことを一級要件とする。ツールの可観測性を最優先する設計思想。

---

## 2. スコープ

### やること（In Scope）
- 一定間隔で「無害な疑似入力」を送り、Windows の無操作タイマーをリセットしてロックを遅延させる。
- 動作状態・送信履歴・次回送信までの残時間を GUI で可視化する。
- 開始 / 停止をユーザー操作で切り替える。

### やらないこと（Out of Scope）
- 会社のグループポリシー（GPO）やレジストリ、アカウント設定の変更は一切しない。
- 管理者権限を要する処理はしない。
- 外部ネットワーク通信・テレメトリ・自動アップデートはしない。
- バッジ抜き取り／Bluetooth近接（Dynamic Lock）等、**入力アイドル以外を契機とするロックの回避はしない**（技術的に不可能。8章参照）。

## 3. 用語

| 用語 | 定義 |
|------|------|
| 無操作タイマー | Windows が「最後の入力からの経過時間」を計測する仕組み。`GetLastInputInfo` で取得できる値が基準。 |
| ロックしきい値 | スクリーンセーバーのタイムアウト、または GPO `Machine inactivity limit`。この時間を超えるとロックが発動する。 |
| 疑似入力 | `SendInput` API でアプリが注入する入力イベント。OS の無操作タイマーをリセットする。 |
| キープアライブ信号 | 本アプリが送る疑似入力（既定は F15 キーの押下→解放）。 |

## 4. 動作モデル（A案で確定）

**プロセスが生きている＝延長が有効。ウィンドウは状態を見るための窓であり、動作の条件ではない。**

- アプリ起動時: **既定で「延長ON」状態で開始する（起動即稼働）**（確定）。
- **ON/OFF は稼働中いつでもトグルで切り替えられる**（FR-7）。ONは初期状態にすぎず、固定ではない。
- ウィンドウを**最小化しても信号送信は継続**する（可観測性 ≠ 動作条件）。
- ウィンドウを**閉じる（×）= プロセス終了 = 延長停止**。分かりやすい停止手段として「閉じれば必ず止まる」を担保する。
- 「停止」ボタン: プロセスは生かしたまま信号送信だけ止める（状態ランプが灰に）。「開始」で再開。

状態遷移:

```
[起動] ──> ON（送信中）
   ON ──[停止ボタン]──> OFF（送信停止・プロセス生存）
   OFF ──[開始ボタン]──> ON
   任意 ──[×で閉じる]──> プロセス終了（延長停止）
```

## 5. 機能要件（FR）

| ID | 要件 |
|----|------|
| FR-1 | 既定 60 秒間隔で キープアライブ信号（F15 の down→up）を1回送信する。 |
| FR-2 | 送信間隔をユーザーが変更できる（候補: 30 / 60 / 120 / 240 秒）。既定 60 秒。**ロックしきい値より必ず短い前提**（ユーザー責任だが、6.6 の注意を UI に添える）。 |
| FR-3 | 送信のたびに、ログ領域へ1行追記する（`HH:MM:SS  F15 送信 ✓`）。 |
| FR-4 | 「次の送信まで」の残り秒数を**毎秒**更新表示する（画面が常に動いていることで生存を示す）。 |
| FR-5 | 状態ランプ（ON=緑 / OFF=灰）で現在の稼働状態を一目で示す。 |
| FR-6 | 累積送信回数を表示する。 |
| FR-7 | 「停止 / 開始」トグルボタンで送信を止める / 再開する。 |
| FR-8 | 最終送信時刻を表示する。 |
| FR-9 | 送信は OFF 状態では行わない。OFF 中はカウントダウンを停止し「停止中」と明示する。 |

## 6. 技術仕様

### 6.1 実行環境 / ビルド
- 言語: Go
- ターゲット: `GOOS=windows GOARCH=amd64`
- 成果物: **単一 .exe**（依存 DLL 同梱不要が理想。GUI ライブラリの選択で cgo 要否が変わる点に注意）。
- 管理者権限不要で動くこと。

### 6.2 キープアライブ信号の送出（最重要）

**必ず「疑似入力（`SendInput`）」で無操作タイマーをリセットする方式にすること。**
`SetThreadExecutionState`（`ES_DISPLAY_REQUIRED` 等）**だけ**では、モニタ電源オフは抑止できても、無操作アイドルで発火するロックは止まらない可能性が高い。ロック回避が目的なので、`SendInput` が本命。保険として `SetThreadExecutionState` を併用してもよいが、主機構ではない。

- 使用 API: `user32.dll` の `SendInput`
- 送るキー: **VK_F15（仮想キーコード `0x7E`）**
  - 理由: F13〜F24 は規格上存在するが物理キーにもアプリのショートカットにも割り当てが無く、どのウィンドウが受け取っても無害に素通りする。フォアグラウンドの作業アプリに飛んでも副作用が出ない。（詳細は 6.6）
- 送出内容: keydown（flags=0）→ keyup（flags=`KEYEVENTF_KEYUP`=`0x0002`）の2イベントを1回の `SendInput` で送る。

主要定数:

| 定数 | 値 |
|------|-----|
| `INPUT_KEYBOARD` | `1` |
| `VK_F15` | `0x7E` |
| `KEYEVENTF_KEYUP` | `0x0002` |

構造体（概略・実装者が Go 側で定義）:

```
INPUT{ Type uint32; <union> }        // Type = INPUT_KEYBOARD
KEYBDINPUT{ Vk uint16; Scan uint16; Flags uint32; Time uint32; ExtraInfo uintptr }
```

> 実装上の落とし穴（要注意）: Win32 の `INPUT` は共用体で、最大メンバは `MOUSEINPUT`。Go で `INPUT` を定義する際は**構造体サイズ／アラインメントを `MOUSEINPUT` 基準に合わせる**必要がある。サイズがずれると `SendInput` が 0（失敗）を返す。`SendInput` の戻り値（送出成功数）を必ずチェックし、0 ならログに「送信失敗」を出すこと。

### 6.3 タイマー設計
- **送信用タイマー**: 設定間隔（既定60s）ごとに信号送出。`time.Ticker` 等。
- **UI カウントダウン用タイマー**: 1秒ごとに「次の送信まで」を再描画。送信用と別に持つ。
- 間隔変更時はカウントダウンを新しい間隔でリセットする。

### 6.4 GUI ライブラリ（実装者が選定・要検証）
小さなステータスウィンドウ（ランプ / ラベル数個 / ドロップダウン / ボタン / ログ用リスト）が作れれば何でもよい。選定基準:

1. 単一 exe で配布しやすい（cgo なし or ビルド容易）
2. Windows ネイティブに近い軽量な見た目
3. メンテナンスが継続している

候補（**採用前に最新のメンテ状況・ビルド要件を必ず確認すること。この仕様作成時点で裏取りしていない**）:
- ネイティブ Win32 ウィジェット系（例: lxn/walk 系）— 軽量・Windows専用
- pure-Go 描画系（例: Gio）— cgo 不要が魅力
- クロスプラットフォームGUI系（例: Fyne）— ただし C コンパイラ／OpenGL 依存の有無を確認

選定理由と、cgo 要否・配布方法（単一exeになるか）を実装時に README へ記録すること。

### 6.5 スレッド / 並行性
- 信号送出はワーカ goroutine で行い、UI スレッドをブロックしない。
- UI 更新（ログ追記・カウンタ・ランプ）は各 GUI ライブラリの流儀で UI スレッドにマーシャリングする（多くの GUI で必須）。
- 停止時はワーカを確実に止める（goroutine リーク・二重送信を作らない）。

### 6.6 F15 が飛ぶ先について（設計の妥当性）
`SendInput` の入力は「現在フォアグラウンドのウィンドウ」に届く。ユーザーは通常、本アプリ以外（ブラウザ・Office等）を操作中なので F15 はそこへ飛ぶ。しかし F15 はどのアプリでもアクション未割り当てのため**無害に無視される**。一方で無操作タイマーは**システムに1つ**なので、どのウィンドウが受け取っても等しくリセットされる。よって本設計は成立する。「無害キーだから行き先を問わない」ことが前提条件。

## 7. 画面仕様

初期案レイアウト（文言・配置は実装で微調整可）:

```
┌─ KeepAlive ───────────────────────┐
│  ● 延長中                          │  状態ランプ: 緑=ON / 灰=OFF＋テキスト
│                                    │
│  次の送信まで:  42s                │  毎秒更新（OFF時は「停止中」）
│  最終送信:      12:03:45           │
│  送信回数:      128                │
│  間隔:          [ 60s ▼ ]          │  30/60/120/240
│                                    │
│  ── ログ ──────────────────────    │
│  12:03:45  F15 送信 ✓              │  新しい行が上（or 下）に追記
│  12:02:45  F15 送信 ✓              │  上限行数を決め、古い行は破棄
│  12:01:45  F15 送信 ✓              │
│                                    │
│         [ 停止 ]                   │  トグル（ON時「停止」/ OFF時「開始」）
└────────────────────────────────────┘
```

表示状態の定義:
- **ON**: ランプ緑・「延長中」・カウントダウン進行・ボタン「停止」。
- **OFF**: ランプ灰・「停止中」・カウントダウン非表示（または「—」）・ボタン「開始」。
- ログは上限行数（例: 直近200行）を保持しリングバッファ的に破棄。

## 8. エッジケース / 制約（実装者が理解しておくこと）

1. **アイドル方式以外のロックは対象外**: 社員証／スマートカード抜き取りロック、Bluetooth近接（Dynamic Lock）は入力注入では防げない。これらが有効な環境では本アプリは効かない。仕様外として扱う。
2. **疑似入力は検知されうる**: 注入入力には `LLKHF_INJECTED` フラグが立つ。高度な監視エージェント（EDR/DLP）はこれを見て「物理入力でない」と判別できる。**本アプリは検知回避を目的にしない**（できないし、しない）。
3. **署名なし exe の実行制限**: 会社PCの AppLocker/WDAC 次第で実行自体が拒否されうる。これは本アプリの実装で解決できる問題ではない（配布・実行可否は別問題）。
4. **間隔 > しきい値だと無意味**: 送信間隔がロックしきい値以上だと防げない。UI に「間隔はロック時間より短く」の注意書きを添える。
5. **多重起動**: 二重起動時の挙動（許可 / 単一インスタンス化）は「9. 未確定」で確認。

## 10. 受け入れ基準（DoD）

1. **動く**: Windows 上でウィンドウが表示され、ON 状態で既定間隔ごとにログが1行増える。
2. **効く（機能検証）**: アプリ ON の状態で、通常ならロックされる時間（しきい値）以上放置してもロックされないこと。
   - 検証手段例: `GetLastInputInfo` の値が送信ごとに現在時刻付近へ更新されることを確認する簡易チェック、または実機で放置してロックしないことを確認。
3. **止まる**: 「停止」で送信が止まり（ログが増えない・ランプ灰）、放置すると通常どおりロックされる。「開始」で再開する。
4. **閉じれば止まる**: × でプロセス終了し、延長が停止する。
5. **可観測**: 動作中は「次の送信まで」が毎秒動き、生存が一目で分かる。
6. **失敗が見える**: `SendInput` が失敗（戻り値0）したらログに失敗として表示する。
7. **副作用なし**: 作業中の他アプリに文字入力やショートカット暴発が起きない（F15 のため）。
8. **単一 exe**: 生成物が単一 .exe で、管理者権限なしに起動できる。
9. **README**: ビルド手順（`GOOS`/`GOARCH`）、採用GUIライブラリと選定理由、cgo要否、既知の制約（8章）を記載。

- 本アプリは**会社のセキュリティ制御（自動ロック）を意図的に遅延させる**ツールである。導入・運用は利用者の責任と所属組織のポリシー次第。

```
