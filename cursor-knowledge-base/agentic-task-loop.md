# Cursor / Claude Code 的な自律タスク消化の設計メモ

2026-06 時点の会話メモ。目的は「いつの間にかある程度仕事が進む」状態を作りつつ、人間のコンテキストスイッチ回数を減らすこと。

## 結論

Cursor IDE 単体の Agent Window は、Claude Code の loop のような「`tasks.md` を監視して、次のタスクを取り続ける常駐ランナー」とは考えない方がよい。

Cursor は IDE 中心の対話型エージェント付き開発環境で、Agent Window は 1 セッション内で大きめの作業を任せる UI。`tasks.md` を読ませて複数タスクを進めることはできるが、永続的な scheduler / daemon / task queue runner ではない。

Claude Code loop に近づけるなら、外側の loop は IDE ではなく CLI / Cloud Agent / GitHub Actions / cron / 社内バッチに持たせる。

```text
外側の loop:
  shell / cron / GitHub Actions / 社内バッチ

1回の作業:
  cursor-agent or Claude Code

作業内の分担:
  subagents
```

## Cursor でできること・できないこと

### Agent Window

できること:

- 1つの Agent セッションに長めの指示を渡す
- `tasks.md` を読ませて、Ready の未完了タスクを処理させる
- 確認を減らす設定で、調査・編集・テストまで進めさせる
- セッション内で複数タスクを順番に処理させる

苦手なこと:

- `tasks.md` を監視し続ける
- 終わったら時間を置いて次を取りに行く
- 失敗時の再試行ポリシーを安定運用する
- IDE セッションをまたいで長時間の自動処理を続ける

### Cursor CLI

会社環境で `cursor-agent` が使えるなら、バッチ的な運用が現実的。

```text
tasks.md
  ↓
外部スクリプト / GitHub Actions / cron / Slack bot
  ↓
cursor-agent -p "tasks.md を読み、Ready の先頭タスクを1件だけ実装して..."
  ↓
テスト実行
  ↓
成功したら Review / Done、失敗したら Blocked
```

Cursor CLI には Subagent 相当の仕組みがある。ただし Subagent は task queue runner ではなく、1回の agent 実行の中で調査・実装・テスト・レビューなどを分担するためのもの。

### Cloud Agents

Cloud Agents は「タスクを渡すと repo を clone し、branch を作って作業し、PR を作る」単位の仕組みとして見る。これも永続 loop そのものではなく、タスク単位の実行基盤。

## 目指すべき運用

完全自律ではなく、注意を奪わない半自律を狙う。

```text
人間:
  週1-2回、tasks.md / GitHub Issues にタスクを補充・優先度付けする

Agent:
  小さめのタスクを1件ずつ拾う
  実装する
  テストする
  PR or 差分を作る
  詰まったら質問ではなく Blocked に理由を書く

人間:
  まとまった時間に Review と Blocked だけ見る
```

重要なのは、Agent が作業中に毎回質問して人間を割り込ませないこと。仕様判断が必要な場合は質問を即時に投げず、Blocked に理由を残して停止する。

## tasks.md の例

```markdown
# Tasks

## Ready
- [ ] ログイン失敗時のエラーメッセージを改善する
- [ ] ユーザー一覧検索に debounce を入れる

## In Progress

## Blocked
<!-- Agent がここに詰まった理由を書く -->

## Review
<!-- 実装済み、人間レビュー待ち -->

## Done
```

## AGENTS.md に置く自律作業ルール例

```markdown
## 自律作業ルール

- `tasks.md` の Ready から上から1件だけ処理する
- 不明点があっても、軽微なものは既存実装に合わせて判断する
- 仕様判断が必要な場合は作業を止め、`tasks.md` の Blocked に理由を書く
- 1タスク1ブランチまたは1PRにする
- テスト、lint、typecheck が通らない場合は Done にしない
- 30分以上詰まったら、それ以上粘らず Blocked にする
- ユーザーへの質問は最後の報告にまとめる
```

## 1タスク処理用プロンプト例

```text
tasks.md を読んで、Ready の一番上の未完了タスクを1つだけ処理してください。

不明点があっても、既存実装から合理的に判断できる場合は質問せず進めてください。
仕様判断が必要な場合は実装せず、Blocked に理由を書いて停止してください。

実装後は test/lint/typecheck を実行してください。
成功したら Review に移し、変更内容と確認結果を書いてください。
一度に複数タスクは処理しないでください。
```

## タスクの分類

自動でやらせやすい:

- 小さいバグ修正
- 文言修正
- テスト追加
- lint 修正
- 型エラー修正
- 軽いリファクタ

半自動:

- 既存画面の改善
- API 追加
- バリデーション追加
- DB に影響しない機能追加

人間主導に残す:

- 仕様設計
- DB 設計
- 認可
- 課金
- 外部連携
- 大きな UI 変更

## 運用イメージ

```text
朝:
  Agent が Ready から1-3件処理

昼/夕方:
  人間は Review と Blocked だけ見る

夜:
  CI が通った PR はレビュー待ち
  詰まったものは Blocked に理由つきで残る
```

## 設計上の勘所

- Agent を賢くするより、Agent が迷わない作業棚を作る
- 質問を即時通知にしない。判断できないものは Blocked に集約する
- 1回の agent 実行は 1 タスクに絞る
- CI を品質ゲートにする
- 人間はタスク供給者兼レビュー者に下がる
- IDE で loop させようとせず、loop は外側の仕組みに持たせる

# 補遺: タスクを置く「基板」の選び方（2026-06 追記）

上の `tasks.md` 単一ファイル版に対し、「個人＋AI用のタスク管理を何の上に載せるか」を整理する。役割は **実行役**（人が起票、AIが拾って作業）前提。

## 基板非依存の4原則

基板が何であれ、実行役で事故らない核はこれ。

1. **ゲート（着手可の明示）** — AIは「着手していい」と明示された課題しか触らない。書きかけ/検討中を拾わせない。最大の事故防止。
2. **自己クローズ禁止** — AIは完了しても「レビュー待ち」で止め、人が承認してDoneにする。AIにDone/closeを持たせない。
3. **自己完結** — 課題本文に 背景 / 前提 / 完了条件(DoD)。薄い課題は迷走の元。
4. **1実行 = 1課題** — 予測可能性のため1回1件。

## 基板の選び方

役割1・個人＋AIなら **まずテキストファイルを検討する**。基板が負けるのは「机から離れて使いたい」系の要件だけ。

| 要件 | テキストファイル | Backlog | Jira |
|---|:--:|:--:|:--:|
| AI実行役の摩擦の少なさ | ◎ | △ | △ |
| Web/モバイルで見たい | ✗ | ◎ | ◎ |
| 通知・リマインド | ✗ | ◎ | ◎ |
| 他人と共有・将来チーム化 | ✗ | ◎ | ◎ |
| 作成の自由度（権限ゲート） | ◎ | ◎ | △ |
| 履歴・監査 | ◎(git) | ◎ | ◎ |

- **自分とAIだけ・1台のマシンで完結** → テキストファイル
- **スマホで見たい / 通知が要る / 自由に使えるSaaSがある** → Backlog
- **既存ドキュメント基盤（Confluence等）と連携したい** → Jira

## テキスト基板の2形態

### 形態1: 単一ファイル（`tasks.md`）

上の本編で扱った形。Ready / In Progress / Blocked / Review / Done を見出しで持つ。手軽だが、件数が増えると1ファイルが肥大化し差分が読みにくい。

### 形態2: ディレクトリ＝ステータス（件数が増えるなら推奨）

ファイルシステムそのものを状態機械にする。**AIはファイル操作がネイティブ**なので、API認証・本文フォーマット変換・ポーリングの摩擦がゼロ。

```
tasks/
  inbox/    ← 下書き（まだ着手させない）
  todo/     ← ここに置く = ready（ゲート = ディレクトリ）
  doing/    ← AIが着手で移動
  review/   ← AI完了で移動して停止（done/ には動かさない）
  done/     ← 人が承認して移動
  blocked/  ← AIが詰まったら
```

- 状態遷移 ＝ `git mv`。別途 status フィールド不要。
- ゲート ＝ `todo/` に在ること。
- git管理すれば**移動履歴がそのまま監査ログ**（`git log` で着手→レビュー送りが追える）。
- タスク = 1ファイル（frontmatter: id/type/priority/created、本文: 背景/前提/DoD/AI作業ログ）。

AIの動作: `todo/` の最優先1件を選ぶ → `git mv` で `doing/` → 作業＆ログ追記 → `git mv` で `review/` して停止。`done/` へは動かさない。

## Backlog / Jira へのマッピング

骨格は同じ。機構だけ読み替える。

| 概念 | テキスト | Backlog / Jira |
|---|---|---|
| ゲート（ready） | `todo/` ディレクトリ | ラベル `ai-ready`（無い課題は触らない） |
| 状態 | ディレクトリ | status（To Do / In Progress / In Review / Done / Blocked） |
| 遷移 | `git mv` | transition API |
| 完了報告 | `review/` へ移動 | `In Review` へ遷移（Doneにしない） |
| タスク種別 | frontmatter `type` | ラベル `research/develop/write` |
| 監査ログ | git log | 課題の履歴 |

### SaaS基板のハマり所（着手前に1件で確認）

- **本文フォーマット**: Jira Cloud REST v3 はコメント/説明が ADF（JSON）。プレーンテキスト/Markdownは弾かれる。AIに書かせるなら v2（wiki記法のプレーン文字列）が楽なことが多い。要検証。
- **検索エンドポイント**: 旧 `GET /search` は廃止方向。現役の検索API（`/search/jql` 等）を1コールで確認。
- **権限**: プロジェクト作成権限は書き込み権限と別管理。作れなければ管理者に1回依頼。
- **APIトークン**: マシンローカルに置く（`.envrc` 等）。リポジトリにコミットしない。

## 共通の鉄則

- シークレット・顧客PII・社外秘はタスク本文に書かない（基板を問わず）。
- gitは**ローカル/private**で。公開リポジトリに業務タスクを載せない。

# すぐ使える: ファイルシステム版の運用ルール（コピペ用）

ルールは**コードリポジトリのルートではなく `tasks/` 直下に置く**（常時ロードのトークン税を避ける）。ファイル名を `AGENTS.md` にすると、バッチで明示的に読ませつつ、`tasks/` をIDEで開いたときは自動ロードもされる。バッチプロンプトは極小にして、ルールはこのファイル側で育てる。

## `tasks/AGENTS.md`

```markdown
# タスクランナー運用ルール（AIエージェント用）

このディレクトリは「人が下書き・AIが整地と実行」する個人タスクボード。
AIは2モードで動き、作業前に必ずこのファイルを読む。
- triage: inbox/ の下書きを検査し、DoDが揃っていれば todo/ へ昇格する
- execute: todo/ のタスクを1件処理し review/ へ送る

## ディレクトリ = ステータス
- inbox/   人の下書き。triageモードのAIが検査する
- todo/    着手可(ready)。**DoD充足済み**。executeが拾うのはここだけ
- doing/   作業中。常に最大1件
- review/  完了・人のレビュー待ち。AIの終着点
- done/    人が承認済み。AIは置かない
- blocked/ 詰まり。理由と再開条件をログに書く

## 不可侵の原則
1. done/ へは絶対に動かさない（クローズは人間のみ）
2. DoD未充足のタスクを todo/ に上げない・実行しない
3. execute は1回の実行で1件だけ。triage は inbox/ 全件を一括でよい
4. 仕様判断が要るときは人に質問せず、blocked/ に理由を書いて停止する

## モードA: triage（inbox → todo 昇格判定）
inbox/ の各ファイルについて DoD充足基準を判定する。
充足基準（すべて満たせば昇格可）:
  - ## 背景 が空でない
  - ## 前提 が空でない（無い場合は「なし」と明記されている）
  - ## 完了条件(DoD) にチェック可能な具体項目が1つ以上ある
判定:
  - 充足   → `git mv inbox/X.md todo/` → commit "promote: X"
  - 未充足 → inbox/ に残し、## triageメモ に「昇格に足りない項目」を
            箇条書きで追記 → commit "triage: X"

## モードB: execute（todo → review 実行）
0. 起動時チェック: doing/ に残骸があれば新規を拾わず再開。再開不能なら blocked/ へ退避
1. 選定: todo/ から priority 高 → created 古 の順で1件
2. 着手: `git mv tasks/todo/X.md tasks/doing/` → commit "pick: X"
3. 種別判定: 作業ログが空＝新規 / ## レビュー指摘 あり＝手直し
   （人が review→todo に戻した分。指摘の解消を最優先）
4. 作業: 本文の DoD を満たすまで。コード変更は test / lint / typecheck を通す
5. 詰まり上限（いずれか1つで blocked/ へ）:
   - 同一エラー（同じ test / lint / typecheck の失敗）の修正を **3回** 試して直らない
   - 1タスクの修正試行が **通算5回** を超えた
   - 前提・DoD が欠けて判断できない（試行を待たず **即** blocked）
6. ログ: 「## 作業ログ」に 実施内容 / 確認結果 / 残課題 を追記
7. 完了: `git mv tasks/doing/X.md tasks/review/` → commit "review: X"
8. 詰まり: `git mv tasks/doing/X.md tasks/blocked/` → commit "blocked: X"。理由と再開条件をログに

## 人間がやること（参考）
- 起票: inbox/ に下書きを置く（DoDは埋めきれなくてよい。triageが指摘する）
- 差し戻し: review/ のファイルに ## レビュー指摘 を追記して todo/ に戻す
- クローズ: review/ を確認して done/ へ動かす

## タスクファイル形式（1タスク=1ファイル）
- ファイル名: `YYYYMMDD-<slug>.md`
- frontmatter: id / type(research|develop|write) / priority(high|normal|low) / created
- 本文: ## 背景 / ## 前提 / ## 完了条件(DoD) / ## 作業ログ
- 任意: ## triageメモ（昇格に足りない点） / ## レビュー指摘（人の差し戻し）

## 鉄則
- シークレット / PII / 社外秘は書かない
- 各遷移を git commit する（移動履歴がそのまま監査ログになる）
```

## バッチプロンプト（極小・変えない）

triage（inbox の整地。起票が溜まったら回す）:

```text
tasks/AGENTS.md を読み、triage モードの手順で inbox/ の全ファイルを検査してください。
DoD が揃っているものは todo/ へ昇格、足りないものは ## triageメモ を追記して inbox/ に残す。
execute（todo の実行）はしないでください。
```

execute（実行。1回1件）:

```text
tasks/AGENTS.md を読み、execute モードの手順で todo/ の先頭タスクを1件だけ処理してください。
複数処理・triage・done/ への移動はしないでください。
```

`cursor-agent -p` / `claude -p` / 手動いずれでもこの1ショットで回る。ルールはプロンプトでなく `tasks/AGENTS.md` 側で育てる。

## 運用の勘所（ファイルシステム版に固有）

- **ゲートはディレクトリ＋triage**: 書きかけは inbox/ に置く。todo/ への昇格はAIのtriageが**DoD充足を基準に**判定するので、todo/ には常に「実行可能なタスクだけ」が入る。executeが拾うものが必ずready、という不変条件が成立する。
- **DoDが不足なら何が足りないかを返す**: triageは未充足タスクを弾くだけでなく `## triageメモ` に欠けている項目を書く。人はそれを見て埋めるだけでよい（埋めるべき点を考えなくて済む）。
- **手直しは差し戻しで回す**: PRのようなレビューUIが無くても、review/ のファイルに `## レビュー指摘` を追記して todo/ に戻せば、次のexecuteが「手直しタスク」として指摘解消を最優先する。
- **クラッシュ復旧**: doing/ に1件しか置かないルールにより、中断は「doing/ に1ファイル残る」状態として可視化される。起動時チェック(手順0)で拾い直す。
- **監査ログ**: 各遷移を commit すれば `git log -- tasks/` が着手→レビュー送りの完全な履歴になる。SaaSの課題履歴に相当。
- **並行実行はしない**: 1実行1タスク＋doing/最大1件で、ロック機構なしでも競合しない。複数同時に回したくなったら、その時に初めてロック（doing/ のファイル名にPID等）を検討する。
