# イベント基盤: 新規Producerアプリ追加のタスクリスト

作成日: 2026-06-10
前提:
- 既存イベント基盤（MSK Serverless / IAM認証 / Producer = API GW + Lambda / Topic = Terraform + 踏み台apply）に追加
- Lambdaの中身のコードは**他チームが作成**。自チームはそれを受け取り、汎用Producerアプリとして基盤に組み込む
- Consumerは**他チーム**。Topic・接続情報・メッセージ仕様を払い出す側
- 役割: 自チーム = Producer基盤の提供側（インフラ・デプロイ・運用・チーム間I/F固定）

---

## Phase 0: チーム間インタフェース固定（最優先・他チーム依存のブロッカー）

ここが決まらないと後続の設計が全部仮置きになる。先に投げて回答待ちの間にPhase 1を進める。

| # | タスク | 依存 | 相手 |
|---|--------|------|------|
| 0-1 | **Lambdaコードの受け渡し仕様を確定**: ランタイム/バージョン、パッケージ形式（ZIP or コンテナイメージ）、ハンドラI/F、外部依存、設定値の渡し方（env / SSM）、コードの置き場所（リポジトリ）、受け渡し期日 | なし | コード作成チーム |
| 0-2 | **メッセージフォーマット仕様の合意**: スキーマ定義（JSONスキーマ等）、バージョニング方針、後方互換の扱い。スキーマレジストリ未使用なのでドキュメントで固定する | なし | コード作成チーム + Consumerチーム |
| 0-3 | **Consumerチームへの提供物リスト合意**: Topic名、接続方式（IAM認証）、Consumer Group命名、提供時期 | 0-2 | Consumerチーム |
| 0-4 | **メッセージ量の見積もり取得**: ピークTPS、メッセージサイズ、増加見込み（Topic設計・スロットリング設計の入力） | なし | コード作成チーム |

**注意**: 0-1の回答でECR要否が確定する（コンテナならECR要、ZIPなら不要）。

## クリティカルパス

```
0-1（コード受け渡し仕様）→ 1-5 → 2-3 → 3-1 → 4-1 → 4-3 → 5-1
0-2（メッセージ仕様）→ 0-3 → Consumerチーム側の準備（並走）
```

他チーム依存は **0-1 / 0-2 / 0-4 / 4-1（Consumer受信確認）** の4点。
ここだけ期日を切って先に投げ、待ちの間に 1-1〜1-6 を仮置きで進める。

## リスク・落とし穴

- **コード受領が遅延**した場合: 2-3以降が連鎖で止まる。0-1で期日と中間確認（例: I/F仕様だけ先行fix）を握っておく
- **メッセージ仕様が口頭合意のまま進む**: スキーマレジストリが無いので、ドキュメント合意をスキップするとProducer/Consumer間の不整合が検知できない。0-2は必ず書面化
- **ECRを先に作ってしまう**: 0-1の回答前に作ると無駄になる可能性。確定後でよい
- **環境差分の暗黙化**: Dev/Stage/Prodのパラメータ差分は1-1の設計書に表で持つ
