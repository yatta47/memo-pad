Kafka Topic設計パターン比較

Entity / Aggregate / Bounded Context / Envelope の4パターンを比較。粒度・スキーマ影響範囲・運用コストの違いを一覧。

1. Topic per Entity

エンティティ単位で1 topic。最も細かい粒度。

粒度エンティティ単位（最細）
典型例users / orders / products
得意単純consumer側で必要なtopicだけ購読可
苦手topic爆発エンティティ数で増殖、数百〜数千になる
スキーマ影響topic単位で閉じる。進化が独立
運用コスト高（数が多いとACL・監視対象が増える）

2. Topic per Aggregate

DDD集約ルート単位。関連エンティティを1 topicに束ねる。

粒度集約ルート単位（中）
典型例order-aggregate / customer-aggregate
得意順序保証同一集約内のイベントが順序維持（keyにaggregate ID）
苦手設計力集約境界の切り方で良し悪しが決まる
スキーマ影響集約内のイベント型は同一topicで進化させる必要
運用コスト中（topic数は適度、DDDが前提知識）

3. Topic per Bounded Context

BC単位でprefixを共有する複数topic。consumerはregex subscribe（payment.*）で束ねる。

粒度1 BC = 複数topic（prefix共有）
典型例payment.charge.completed, payment.refund.issued → payment.* で束ねる
得意境界明確topic所有者 = BCチームで一致。consumerは必要な部分集合だけregex選択可
苦手命名規約依存prefix命名の統制が崩れると検索性が落ちる
スキーマ影響BC内で命名・スキーマ規約を統一。チーム単位の契約管理
運用コスト中（topic数は増えるがBC内に閉じる、ACLもprefix単位で制御可能）

4. Envelope Topic

複数イベント型を1 topicに。event_typeフィールドで分岐。

粒度1 topicに多型イベント
典型例order-events（event_typeで分岐）
得意順序完全保証全イベント型がグローバル順序維持
苦手消費効率consumerが不要なイベント型もfetch・filter必要
スキーマ影響Envelope（共通外殻）+ polymorphic payload設計が必須
運用コスト低（topic数最小）、ただしスキーマ設計コスト高

パターンの考え方と適用場面

1. Topic per Entity

考え方

DBのテーブル設計の考えを Kafka に持ち込んだパターン。イベント駆動というよりデータ駆動（state-oriented）で、Kafka を RDB の CDC/レプリカとして使う構造になりがち。

Compacted Topic + Debezium の組み合わせが典型例。CDC（Change Data Capture）で自動生成される topic はほぼ全て Entity 単位になるため、このパターンは既存DBから自然に生まれやすい。

業務アーキテクチャから見た適用場面

  • マスタデータ配布基盤: Customer master / Product catalog など、単一 Entity の最新状態を複数の下流システムに配布したい
  • 既存システムの段階的イベント化: 既存の CRUD/RDB ベースのシステムに手を入れず、Debezium 等の CDC で自動的に entity 単位の topic を生やす
  • データレイク / DWH 連携: 各 Entity の変更履歴をそのまま分析基盤に流し込む
  • Compacted Topic による参照用ストア: Kafka を「常に最新状態が取れるレプリカDB」として使うケース

2. Topic per Aggregate

考え方

DDD = Domain-Driven Design（Eric Evans 2003）のAggregate単位で切るパターン。「ドメイン（業務領域）駆動設計」で、Aggregate（集約）は「一貫性を保つ単位」を指す。例えば Order と OrderItem は別 entity だが「Order 集約」として一塊で扱う。

一見 consumer の filter 負担が大きそうに見えるが、同一 aggregate 内のイベントは key = aggregate ID で順序保証される。OrderCreated → OrderItemAdded → OrderPaid → OrderShipped が順番通りに届き、consumer は必要な event_type だけ反応すればよい。filter 問題はむしろ Envelope の方が重い。

本命の利点は「順序保証」と「Outbox Pattern との親和性」。Producer 側が1集約の変更を1 topic に閉じて書けるので、DBトランザクションと Kafka 送信の整合性が取りやすい。

業務アーキテクチャから見た適用場面

  • 業務トランザクションの外部通知: 1集約（Order / Invoice / Subscription 等）の状態遷移を順序保証で下流に伝えたい
  • Outbox Pattern との組み合わせ: DB書き込みと Kafka 送信の整合性を担保したいとき第一候補（outbox テーブル 1集約単位 → aggregate topic）
  • Saga Pattern の実装基盤: 集約単位で分散トランザクションを組み、補償イベントも同じ topic で扱う
  • DDDベースの業務システム: ドメインモデルが集約で綺麗に切れている、または切ろうとしている組織。集約境界 = topic 境界で整合する

3. Topic per Bounded Context

考え方

ビジネス境界線（Bounded Context）で切るパターン。「支払処理.完了」のようにドットでつないだ形が日本語でも直感的で、実務では ASCII に落として payment.charge.completed のような命名が標準。

  • 各イベントが独立した topic
  • consumer は /^payment\..*/ のような regex で必要な部分集合だけ購読
  • チーム所有も prefix 単位で明確（ACL も prefix で制御可能）

4パターンの中で「イベント駆動」の感覚が一番強く出るのがこのパターン。チーム境界と topic 境界を揃えたい組織で現実解になりやすい。

業務アーキテクチャから見た適用場面

  • マイクロサービス間でデータを複数活用したいとき: ある BC のイベントを他の複数 BC が部分的に購読して活用する。疎結合で横串の連携を取るケース
  • チーム構造とシステム構造を一致させたい組織: Conway's Law と整合。各 BC チームが自分の topic 群の契約を主権的に管理できる
  • API 直接呼び出しからイベント駆動へ移行したいとき: 従来の同期 REST 連携を非同期に置き換え、可用性・疎結合性を上げる
  • 下流システムごとに必要な部分集合が違う場合: 分析系は payment.* を全部、通知系は payment.charge.* だけ、のように regex subscribe で切り分けられる
  • ACL・所有権を BC 単位で管理したい運用要件: prefix ベースで権限制御しやすく、責任境界が明確

4. Envelope Topic（Aggregateとの違いが重要）

考え方

Aggregate と構造（1 topic に複数 event type）は似ているが、境界の切り方が違う。

Aggregate TopicEnvelope Topic
境界の論理DDDの一貫性境界「全体の順序が欲しい」という業務要件
典型サイズ小〜中（1集約、数〜十数種のevent）大（数十〜百種、複数集約横断）
key設計aggregate IDentity ID や無指定（順序優先）
順序保証範囲1 aggregate 内topic全体（同一 partition 内）
典型用途業務イベント監査ログ・金融取引・Event Sourcing永続ログ

Envelope の本命は「全イベントのグローバル順序が業務要件」なとき: 金融取引の監査証跡、コンプライアンス用の操作ログ、Event Sourcing の永続ログなど。

※ Kafka→Kafka でフィルタして個別 topic に振り分けるのは Topic設計ではなく Routing Pattern の話。ただし実務では Envelope + Routing のハイブリッドがよく使われる:

  1. Producer → Envelope topic（例: all-events）
  2. Kafka Streams / Kafka Connect で event_type ごとに split → 個別 topic（例: events.order.paid）
  3. 下流 consumer は個別 topic を購読

これは「全順序維持 + consumer の扱いやすさ」を両立するパターン。Envelope の弱点（consumer の filter 負担）を Stream Processing で吸収する。

業務アーキテクチャから見た適用場面

  • 監査・コンプライアンス基盤: 全操作の時系列追跡が業務要件。誰が何をいつしたかを順序保証で記録する
  • 金融取引・会計システム: 全イベントのグローバル順序が法令・監査要件として必須
  • Event Sourcing の永続ログ: アプリの状態再構築に使う真実のログとして、順序と完全性が最重要
  • SIEM / 操作ログ基盤: 複数サービスの操作を1タイムラインで分析したい。時系列そのものがプロダクトになる用途
  • IoT / テレメトリ集約: 大量のセンサーイベントを時系列で一次集約し、下流で Stream Processing（Routing Pattern）で振り分けるハブとして使う

選び方ガイド

  • Entity: PoC・小規模、各エンティティが独立して進化するケース。CDC で自動生成する topic もここに該当。大規模では topic 数で破綻するので避ける
  • Aggregate: DDD を実践している組織。集約ルートのイベントを順序保証したいとき第一候補。Outbox Pattern との相性が良い
  • Bounded Context: マイクロサービス境界と topic 所有を一致させたい運用寄り設計。チーム所有の明確さと運用負荷のバランスが良く、多くの組織で現実解になりやすい
  • Envelope: 全イベントのグローバル順序が必須な業務（監査ログ、金融取引、Event Sourcing）。スキーマ設計コストを受け入れる前提

混在も可。例: Bounded Context を基本、特定領域（監査）だけ Envelope。最初から綺麗に分類せず、運用で困ったら分離・統合する方針が現実的。
